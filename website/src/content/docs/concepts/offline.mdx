Ramose treats offline support as a database property, not a UI cache. Every activated graph has one complete, authorized, principal-scoped local database at an opaque revision.

## Activation is lazy

Creating a root or child handle is synchronous and inert. A graph activates when the first observed query or mutation needs it. Only activated graphs synchronize; merely being reachable does not download a sibling.

Once activated, a graph stays synchronized for that client session. A later session restores its last complete value and reactivates it lazily.

## The committed replica is always complete

Initial synchronization installs a complete snapshot atomically. Resume applies each visible committed change atomically. The application sees the previous complete value or the next complete value, never half of a snapshot or transaction.

Query results are not persisted. Local indexes derive every answer from the database, which is why a query written tomorrow can still run over yesterday's offline replica.

## Optimistic state is layered

The visible local value is:

```text
committed database
  + queued optimistic projection 1
  + queued optimistic projection 2
  + …
```

Commit installs the server result and removes the corresponding layer. Rejection removes only that layer, then replays later projections. The committed database never contains pending metadata; live entity handles expose it separately through `.local`.

## The outbox survives failure

Invocations, client-created references, queue order, and receipts are persisted separately from the replica. Restart restores both the committed value and the exact speculative view. Reconnect resumes synchronization, submits in order per graph, and uses durable server receipts to recover lost acknowledgements safely.

## One browser, one replica

Tabs coordinate through browser locks, IndexedDB, and broadcast messages. One leader owns server synchronization; every tab can enqueue. If the leader closes, crashes, or is suspended part-way through a durable write, another resumes: the write either landed whole or not at all, and queued work is never lost. A leader whose durable write is refused because another tab has taken over stops retrying and stands for the election again rather than repeating a pass that cannot land. Where the browser offers no lock manager, every tab synchronizes for itself: correctness is unchanged, because concurrent writers converge on the same durable records, but the work is duplicated.

IndexedDB is what every tab agrees on. Broadcast messages only say that something changed and where, so a tab reads the durable records to learn what changed; they order nothing and carry no values. A tab that misses one — because the browser offers no broadcast channel, or because it was suspended — reads the same records when it is next activated and reaches the same state, later rather than never.

A tab that never resolved a graph child can still queue work for it, and the leader that submits it may be a tab that never walked that path. The path each database was last confirmed at is recorded durably, and the leader activates it again to submit: the current names go back to the server, which re-authorizes them, and only a confirmation naming the same database becomes a submission target. A path renamed since it was recorded therefore leaves the queue where it is rather than submitting it somewhere else.

Under storage pressure, Ramose may evict inactive child graphs as complete units. It does not evict the active root, outbox, receipts, or part of a graph. A tab reading a database another tab evicts sees the whole database or none of it.

## Clearing and changing principals reaches every tab

`clearLocalData()` and a principal replacement fence every tab of that principal, including one whose activation is in flight and has not authenticated yet. The barrier is durable: IndexedDB records what was cleared, every install re-reads it inside the transaction that would write, and a tab that never received a broadcast — suspended, restored from bfcache, or on a browser with no broadcast channel — is refused just the same. A fenced tab withdraws what it was showing rather than leaving it on screen, and activates again; the credential the application presents then decides what it shows next.

An activation refused for authentication leaves the client usable. `auth()` runs once per activation, so signing in again and returning to the tab activates with the refreshed bearer. `close()` and `clearLocalData()` are what end a client instance.

## Security remains observable offline

Revocation, policy changes, graph-path changes, and read-view changes cause authorized resets or removals. Hidden-only server activity produces no visible frames, count gaps, queue signals, or diagnostic metadata. Offline data is locally retained application data; use the same device and session threat model you would use for any offline-capable product.
