Most databases give you one global namespace and ask you to simulate boundaries with tenant keys. Ramose makes boundaries structural. A row in one graph can be an authorized doorway to another graph with its own catalog, policy, history, synchronization, and writer.

## A graph is an ordinary row and a separate database

An entity composes `Ramose.Graph(childCatalog)`. That binding adds graph metadata and fixes the child catalog in deployed code. Creating the entity creates the parent row atomically; child storage is acquired only after a caller authorizes the complete path.

```ts
export const Project = Ramose.Entity(
  "project",
  { title: Ramose.string() },
  { traits: [Ramose.Graph(ProjectCatalog)] },
)
```

Many `Project` rows can use `ProjectCatalog`. They still open distinct child databases.

## Address and identity are different

Humans and agents address a graph by readable names: `at: ["acme", "launch"]`. The server resolves each name through the parent's authorized filtered value. After it sees the Graph row, it derives the stable child identity from the parent identity and the row identity.

Renaming `launch` changes the path but not the child database. References still point to the same row. Data does not move, copy, or rebind to another catalog.

## Authorization is checked at every boundary

Opening a child requires:

1. a valid deployment-wide identity token;
2. visibility of every ancestor Graph row and required path field;
3. successful server-owned catalog resolution for each child;
4. the child graph's independent policy for its contents.

Parent readability is not child content access. A hidden ancestor makes the whole descendant inaccessible. Missing, hidden, archived, misconfigured, and unavailable paths intentionally have the same public shape.

## What a child graph does not inherit

A child does not inherit parent rows, query scope, operation grants, or write capacity. Cross-graph joins and atomic multi-graph writes do not exist. Carry the minimal contextual identity into the child as immutable or duplicated facts when the child needs it, and reconcile across graphs through explicit workflows.

## The three performance boundaries

Graph boundaries determine three costs:

- **Write throughput:** every graph has one ordered writer. Independent children write in parallel.
- **Offline footprint:** an activated graph is replicated completely for one principal. Inactive child graphs can be evicted as units.
- **Query scope:** local and server queries stay inside one graph, so indexes and intermediate work are bounded by that graph's size.

More graphs reduce per-graph cost and improve isolation, but add path checks, synchronization streams, workflow coordination, and duplication. The best boundary is usually a unit with independent ownership, lifecycle, and high write locality.

## Lifecycle

Archiving a graph hides it from ordinary discovery and path resolution while retaining its row, name reservation, catalog binding, history, references, and child storage. Restoring reopens the same graph. Permanent purge and recataloging are different operations and are not part of the model.
