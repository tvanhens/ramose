This page is the mental model behind Ramose, in plain words, for someone who has run the Quickstart and wants the guides to make sense. It assumes nothing about databases.

## A database is a pile of facts

A **record** is one thing in the database — an issue, a user ([glossary](/concepts/glossary/#record)). A **field** is one named, typed slot on it, like `issue.title` ([glossary](/concepts/glossary/#field)). Group the fields and you have a **record type** — a kind of record, like a table ([glossary](/concepts/glossary/#record-type)).

Ramose does not store an issue as a row. It stores **facts**: *issue 17's title is "Fix login"*, *issue 17's status is "todo"* ([glossary](/concepts/glossary/#fact)). A record is the set of facts about one id. That is the whole storage model; everything on this page follows from it.

## Nothing is overwritten

Move issue 17 to Done and Ramose does not edit the status fact. It adds a new one (*status is "done"*) and marks the old one as gone. Both stay on file.

A **write** is one all-or-nothing group of changes ([glossary](/concepts/glossary/#write)). Every write gets the next **version number `t`** ([glossary](/concepts/glossary/#version-number)). The picture above is the database at version 9. Read it at version 8 and the status is still "todo". That is all Reef's time-travel slider does.

## Reading means asking at a version

Every read happens at a version. You pick which one:

- **Now, and again on every change** — a **live query** re-runs itself whenever the version moves and hands your screen new rows ([glossary](/concepts/glossary/#live-query)). Reef's board is one.
- **As it was** — `db.asOf(t)` reads at an earlier version ([glossary](/concepts/glossary/#as-of)). Reef's slider is one.
- **Including what was removed** — `db.history` also returns facts marked gone ([glossary](/concepts/glossary/#history)). Reef's "Deleted, still in history" strip is one.

The query is the same value in all three cases. [Time travel](/concepts/time-travel/) shows the code.

## A database is a name

A **database** is a named, isolated pile of facts ([glossary](/concepts/glossary/#database)). `ramose.db("coral-team", Reef)` names one; nothing is created until the first write lands. Each name has its own **writer** — the one thing that commits its writes, in order ([glossary](/concepts/glossary/#writer)) — so two databases never wait on each other.

Because a database is only a name, one per customer is a function call, not a deployment. Every Reef workspace is a database. [One database per customer](/guides/workspaces/) walks through it.

## Rules live with the data

The **policy** is a value that says which roles may read, create, change or remove which fields ([glossary](/concepts/glossary/#policy)). The server checks it on every write and filters every read with it, so a rule holds no matter which screen or script is asking. It is deny by default: forgetting a rule closes a door, never opens one.

Rules are about facts, so they can be precise: in Reef, a member may change an issue *they created*, and only admins ever receive the admin note. Because the policy and the fields your screens read are both values, the deploy checks them against each other — see [the deploy-time check](/guides/permissions/#the-deploy-time-check).

## The schema is a value

The **schema** is your data model as one TypeScript value ([glossary](/concepts/glossary/#schema)). It is written into a database as an ordinary write, `db.install()`. Adding a record type or a field is adding facts about the schema, at a version, like any other write. Nothing rewrites old data, so there is no migration step that can fail halfway. [Changing a schema later](/guides/catalog/#changing-a-schema-later) has the details.

## Where the ideas come from

These ideas — facts instead of rows, a database you can read at any earlier version, one writer and many readers — come from **Datomic**, which inspired Ramose. You do not need to know Datomic to use Ramose. If you do know it: Ramose re-homes the shape on Cloudflare, with a typed query builder instead of a query language, no JVM and no create-database call.

<details>
<summary>If you know Datomic: names, side by side</summary>

| Datomic | Ramose |
| --- | --- |
| datom `[e a v t]` | a fact; the same order on `t` |
| schema transacted as data | a **schema** of TypeScript values; `db.install()` or `Server({ databases })` writes it, safe to repeat |
| `d/transact` with tx-data | `db.transact(function* (tx) { … })` — a generator of `set` / `remove` / `delete` |
| tempids resolved in the transactor | `tx.entity()` — the new ids are **not** returned; query for them |
| `:db.unique/identity`, lookup refs | `{ unique: "upsert" }`, `[User.sub, "…"]` |
| `:db.cardinality/many` | `{ cardinality: "many" }` |
| `d/pull` | `db.pull({ id }, shape)`, same nesting; `.optional` for absence, `.orDefault(v)` for a pull `:default` |
| Datalog query | a typed value — `Query.from(Issue).where(…).select(…).orderBy(…).limit(n)`, run by `db.query` / `db.live`; the combinators are listed under [Filter](/guides/queries/#filter). Single-row terminals and keyset paging ride the value (`q.one()`, `q.after(cursor)`); named rules give recursion ([the query language](/reference/query-language/)) |
| `d/as-of`, `d/history` | `db.asOf(t)`, `db.history` — pure functions to a read-only view |
| transaction entity | `report.txEid` |
| `d/filter` | a compiled **policy**, evaluated per request against the token's claims |
| peer library, JVM | one Cloudflare Worker you declare, not write |

</details>
