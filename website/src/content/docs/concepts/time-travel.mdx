Ramose never overwrites the history of a field. Every committed operation produces a new immutable database value. Current reads use the latest value; temporal queries select another view over the same database.

<Learn learn={["The difference between current, as-of, and history views", "Why current policy governs historical data", "Which recovery and audit workflows temporal queries support"]} before={[{ href: "/concepts/data-model/", label: "Data model" }]} minutes={6} />

## Current

The normal database is the latest committed value plus any client-local optimistic layers. Server reads use only committed state. The database has one ordered version sequence.

## As of

An as-of query asks what the database looked like at or before an earlier version. The schema and policy come from the current deployment; the application facts come from the selected immutable value.

```ts
const yesterday = projectDb.asOf(version)
const tasks = yesterday.query.from(Task).where({ done: false })
```

As-of views are read-only. They are not branches and do not rewind the current database. Recovery is an explicit current operation that reads the desired past state, validates it, and writes a new present.

## History

History queries expose when visible statements were added or removed. Use them for audit trails, change explanations, conflict UI, and recovery tooling. They do not expose raw storage records or hidden transaction metadata.

## Authorization over time

Current deployed policy and current grants govern historical reads. Revoking a principal removes access to past data too. The engine classifies historical facts by their concrete identity at the requested value, including facts from entities later deleted, then filters them before query semantics.

## Retention and deletion

Logical history is distinct from retained index snapshots. Storage maintenance may discard old physical roots while the current index still retains the facts needed for temporal reads.

Application deletion hides an entity from the current value but preserves history. Regulatory erasure requires a separate data-lifecycle strategy; do not store secrets that must become unrecoverable without that design.
