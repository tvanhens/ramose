<p class="rg-eyebrow">Try it in two minutes</p>

<p class="rg-run-note"><strong>Ripple is pre-release and not on npm yet</strong> — you run it from the repository. Bun, one clone, no account, no external database.</p>

```sh title="From the repository root" frame="terminal"
git clone https://github.com/tvanhens/ripple && cd ripple
bun install

CI=1 ALCHEMY_STATE=local \
  CLOUDFLARE_ACCOUNT_ID=0123456789abcdef0123456789abcdef \
  CLOUDFLARE_API_TOKEN=x \
  bun alchemy dev examples/todos/alchemy.run.ts       # the database, on :1337

VITE_RIPPLE_URL=http://localhost:1337 bunx vite examples/todos   # the app, on :5173
```

<p class="rg-run-after">Open <code>http://localhost:5173</code> and add a todo. The list re-renders from the database, and the app code never refetches. <span class="rg-caveat">Two tabs stay in sync on a deployed database; on the local emulator a change in one tab reaches the other on reload.</span></p>

    <h2>The schema is TypeScript</h2>
    <p>
      A catalog is a plain value: the attributes an entity can carry, their
      types, whether one is unique, whether it holds one value or many. The
      same file is read by your app, your Worker, and your deploy. No codegen,
      no migration step, and changing it never rewrites data you already wrote.
    </p>
  </div>
  <div class="rg-moment-code">

```ts title="schema.ts"
import * as Ripple from "@ripple/alchemy/db";
import * as Schema from "effect/Schema";

export const User = Ripple.Namespace("user", {
  sub: Ripple.Attr(Schema.String, { unique: "identity" }),
});

export const Todo = Ripple.Namespace("todo", {
  title: Ripple.Attr(Schema.String),
  done: Ripple.Attr(Schema.Boolean),
  createdAt: Ripple.Attr(Ripple.Instant),
  owner: Ripple.Attr(Ripple.Ref(() => User)),
});

export const Todos = Ripple.Catalog({ user: User, todo: Todo });
```

```ts title="todos.ts"
await run(
  db.transact(function* (tx) {
    const todo = yield* tx.entity();
    yield* todo.add(Todo.title, "ship the landing page");
    yield* todo.add(Todo.done, false);
    yield* todo.add(Todo.createdAt, new Date());

    // Does not compile — `todo/done` is a boolean, so
    // this write never gets past your editor:
    // yield* todo.add(Todo.done, "false");
  }),
);
```

<div class="rg-moment rg-moment--flip">
  <div class="rg-moment-copy">
    <h2>One query, always current</h2>
    <p>
      <code>db.live</code> hands you a stream of rows. Anything that changes the
      answer — this tab, another tab, another user, a Worker — pushes the rows
      again. There is no cache to invalidate and no refetch call at the write
      site.
    </p>
    <p class="rg-aside">
      Ripple ships no React package. <code>useLive</code> below is twelve lines
      in the example app that turn a stream into state, and you can read all of
      them.
    </p>
  </div>
  <div class="rg-moment-code">

```ts title="todos.ts"
export const todoShape = {
  id: Todo.id,
  title: Todo.title,
  done: Todo.done,
  createdAt: Todo.createdAt,
} as const;

// A value, not a callback: `db.q` runs it once,
// `db.live` keeps it standing.
export const todoQuery = Ripple.query(Todo)
  .orderBy(Todo.createdAt, "asc")
  .select(todoShape);
```

```tsx title="App.tsx"
// built once, outside render — a standing query, not a fetch
const todos = db.live(todoQuery);

const TodoList = () => {
  const { rows, error } = useLive(todos);
  if (error !== undefined) return <p>offline…</p>;
  if (rows === undefined) return <p>loading…</p>;
  return (
    <ul>{rows.map((r) => <Row key={r.id} row={r} />)}</ul>
  );
};
```

  <div class="rg-moment-copy">
    <h2>Permissions are part of the database</h2>
    <p>
      One policy says who may read and write each attribute. Reads are filtered
      before they leave the edge, so a query simply returns fewer rows. Writes
      are checked twice — once on the way in, then again by the writer against
      the exact data the transaction would apply to. An attribute with no rule
      is denied.
    </p>
    <p class="rg-aside">
      Ripple verifies tokens, it never issues them: bring Clerk, Auth0, WorkOS,
      or any issuer with a JWKS endpoint.
    </p>
  </div>
  <div class="rg-moment-code">

```ts title="policy.ts"
const P = Ripple.Policy;

// The token's `sub` claim resolves to a user entity.
export const policy = P.policy(Todos, {
  principal: User.sub,
  classes: ["member"],
  ns: {
    user: { read: P.allow(P.eq(User.sub, P.claims.sub)) },
    todo: {
      read:    P.allow(P.eq(Todo.owner, P.principal)),
      create:  P.allow(P.class("member")),
      add:     P.allow(P.eq(Todo.owner, P.principal)),
      retract: P.allow(P.eq(Todo.owner, P.principal)),
      retractEntity: P.allow(P.eq(Todo.owner, P.principal)),
      // every new todo is stamped with its owner
      preset: [P.preset(Todo.owner, P.principal)],
    },
  },
});
```

```ts title="app.ts"
// Ada is signed in. Todo 1042 belongs to someone else.
await run(db.transact(function* (tx) {
  yield* tx.add(1042, Todo.title, "mine now");
}));

// Unauthorized — 403, code "policy", attr ":todo/title"
//   refused at the edge, before the write travels on
// TxRejected — 409, no transaction number is spent
//   refused by the writer, against the real data
```

```ts title="alchemy.run.ts"
// `pulls` are the shapes your app reads. If the policy
// narrows an attribute one of them requires, the deploy
// fails here — before the rule can quietly drop rows
// from somebody's screen.
Ripple.Policy.compile(policy, { pulls: [todoShape] });
```

<h2 class="rg-h2">What you get</h2>

<div class="rg-benefits">
  <div class="rg-benefit rg-benefit--lead">
    <h3>A mistyped write does not compile</h3>
    <p>
      Attribute names, value types, cardinality and uniqueness all come from
      the catalog, so <code>tsc</code> checks every write and every query shape
      against it. The bad write is a red squiggle in your editor, not a row in
      production.
    </p>
  </div>
  <div class="rg-benefit rg-benefit--lead">
    <h3>Queries update themselves</h3>
    <p>
      A standing query rides one WebSocket per page. Every write moves the
      whole connection forward, and each standing query re-runs against the new
      state — no polling, no invalidation, nothing to remember at the write
      site.
    </p>
  </div>
  <div class="rg-benefit">
    <h3>Every user sees only their rows</h3>
    <p>
      One policy, enforced in two places: reads are filtered before they leave
      the edge, writes are re-checked inside the writer. Deny by default, per
      attribute, so a field you add tomorrow is not world-readable today.
    </p>
  </div>
  <div class="rg-benefit">
    <h3>Nothing is overwritten</h3>
    <p>
      Writes append facts, so <code>db.asOf(t)</code> reads the database as it
      was at an earlier transaction and <code>db.history</code> shows what
      changed. Reach is bounded by retained checkpoints — 20 by default — so
      pick that number deliberately; it is not "forever".
    </p>
  </div>
</div>

<h2 class="rg-h2">Instead of what?</h2>

<p class="rg-lede">
  Ripple is small and pre-release on purpose. Here is the honest trade against
  what you are probably using today.
</p>

<div class="rg-vs">
  <div class="rg-vs-row">
    <h3>Postgres + an ORM</h3>
    <p>You keep the types and lose SQL. No migration ever rewrites old data and live queries come standard — but there is no SQL, no planner to tune, no <code>psql</code>, and no joins across two databases.</p>
  </div>
  <div class="rg-vs-row">
    <h3>Convex</h3>
    <p>A similar "the query re-runs itself" model, deployed into your own Cloudflare account instead of a hosted platform. There is also no dashboard, no scheduled functions, and no file storage.</p>
  </div>
  <div class="rg-vs-row">
    <h3>Supabase</h3>
    <p>Row rules are here, per attribute and deny-by-default, and they run at the edge. Ripple only verifies JWTs, though: bring your own identity provider, and bring your own file storage.</p>
  </div>
  <div class="rg-vs-row">
    <h3>Instant</h3>
    <p>The same instant-graph-in-the-browser feel with per-user permissions, except you own the deployment end to end. Nothing is hosted for you and there is no admin console.</p>
  </div>
</div>

<p class="rg-limits">
  <strong>What Ripple does not have:</strong> SQL · an npm package (clone the
  repo) · a hosted dashboard · joins across databases · more than low thousands
  of writes per second per database · an identity provider of its own.
</p>

</div>

<h2 class="rg-h2">How it works</h2>
<p class="rg-lede">Three moving parts, all of them provisioned by one deploy.</p>

<div class="rg-how">
  <div class="rg-how-box">
    <span class="rg-step">01</span>
    <h3>One writer</h3>
    <p>Each database has exactly one thing that commits writes, in order. No write conflicts to resolve, no leader election, no "eventually".</p>
  </div>
  <div class="rg-how-box">
    <span class="rg-step">02</span>
    <h3>Durable storage</h3>
    <p>A write is in object storage before your call returns. Old files are never rewritten, which is exactly why you can still read yesterday.</p>
  </div>
  <div class="rg-how-box">
    <span class="rg-step">03</span>
    <h3>Readers at the edge</h3>
    <p>Queries run next to your app, against copies of that storage, so reads never wait behind writes and a slow query cannot stall a commit.</p>
  </div>
