<p class="rg-eyebrow">Try it in two minutes</p>

<p class="rg-run-note"><strong>Ripple is pre-release and not on npm yet</strong> — you run it from the repository. One command starts the database and the app together.</p>

```sh title="From the repository root" frame="terminal" wrap
git clone https://github.com/tvanhens/ripple && cd ripple
bun install
bun run dev:todos     # peer on :1337, app on :5173
```

<p class="rg-run-after">Open <code>http://localhost:5173</code> and add a todo. The list re-renders from the database, and there is no refetch call anywhere in the app — that is <code>db.live</code>, working locally. <span class="rg-caveat">On the local emulator writes do not cross isolates, so a second tab picks them up on reload; your own tab always updates, and against a deployed peer every connected client does.</span></p>

<p class="rg-run-more">Want the bigger one? <code>bun run dev:reef</code> boots <a href="https://github.com/tvanhens/ripple/tree/master/examples/reef">Reef</a> — a Linear-style issue tracker, one database per workspace, behind Better Auth JWTs and a compiled policy:</p>

    <h2>The schema is TypeScript</h2>
    <p>
      A catalog is a plain value: the attributes an entity can carry, their
      types, cardinality, and whether one is unique. Your app, your Worker and
      your deploy all read that one file — no codegen, no migration step, and
      changing it never rewrites data you already wrote.
    </p>
  </div>
  <div class="rg-moment-code">

```ts title="schema.ts"
import * as Ripple from "@ripple/alchemy/db";
import * as Schema from "effect/Schema";

export const User = Ripple.Namespace("user", {
  sub: Ripple.Attr(Schema.String, { unique: "identity" }),
});

export const Todo = Ripple.Namespace("todo", {
  title: Ripple.Attr(Schema.String),
  done: Ripple.Attr(Schema.Boolean),
  createdAt: Ripple.Attr(Ripple.Instant),
  owner: Ripple.Attr(Ripple.Ref(() => User)),
  /** private: only the owner reads it — see policy.ts */
  note: Ripple.Attr(Schema.String),
});

export const Todos = Ripple.Catalog({ user: User, todo: Todo });
```

```ts title="todos.ts"
await run(
  db.transact(function* (tx) {
    const todo = yield* tx.entity();
    yield* todo.add(Todo.title, "ship the landing page");
    yield* todo.add(Todo.done, false);
    yield* todo.add(Todo.createdAt, new Date());

    // Does not compile — `todo/done` is a boolean, so
    // this write never gets past your editor:
    // yield* todo.add(Todo.done, "false");
  }),
);
```

  <div class="rg-moment-copy">
    <h2>One query, always current</h2>
    <p>
      <code>db.live</code> hands you a stream of rows. Anything that changes the
      answer — this tab, another tab, another user, a Worker — pushes the rows
      again. There is no cache to invalidate and nothing to remember at the
      write site.
    </p>
    <p class="rg-aside">
      Ripple is built on <a href="https://effect.website">Effect</a>: a
      transaction is a generator, and <code>run(…)</code> is the runtime you set
      up once in the example's <code>db.ts</code>. There is no
      <code>@ripple/react</code> package yet — <a href="https://github.com/tvanhens/ripple/blob/master/examples/todos/src/useLive.ts"><code>useLive</code></a>
      is about a dozen lines you copy once, and the only React glue Ripple needs.
    </p>
  </div>
  <div class="rg-moment-code">

```ts title="todos.ts"
export const todoShape = {
  id: Todo.id,
  title: Todo.title,
  done: Todo.done,
  createdAt: Todo.createdAt,
} as const;

// A value, not a callback: `db.q` runs it once,
// `db.live` keeps it standing.
export const todoQuery = Ripple.query(Todo)
  .orderBy(Todo.createdAt, "asc")
  .select(todoShape);
```

```tsx title="App.tsx"
// built once, outside render — a standing query, not a fetch
const todos = db.live(todoQuery);

const TodoList = () => {
  const { rows, error } = useLive(todos);
  if (error !== undefined) return <p>offline…</p>;
  if (rows === undefined) return <p>loading…</p>;
  return (
    <ul>{rows.map((r) => <Row key={r.id} row={r} />)}</ul>
  );
};
```

    <h2>Permissions are part of the database</h2>
    <p>
      One policy says who may read and write each attribute. Reads are filtered
      before they leave the edge, so a query simply returns fewer rows. Writes
      are checked twice: on the way in, then again by the writer against the
      exact data the transaction would apply to. Deny by default — an operation
      is allowed only if a rule allows it, and when an attribute carries its own
      rule both it and its namespace rule must allow, so an attribute rule can
      only narrow.
    </p>
    <p>
      The policy and the shapes your app reads are both values, so
      <code>Ripple.Policy.compile</code> checks them against each other at
      deploy time: tighten a rule a screen depends on and the deploy fails,
      rather than that screen quietly emptying for one customer.
    </p>
    <ol class="rg-frames">
      <li>the policy</li>
      <li>what a refused write looks like</li>
      <li>the deploy-time check</li>
    </ol>
    <p class="rg-aside">
      Ripple verifies tokens, it never issues them — bring Clerk, Auth0,
      WorkOS, or any JWKS issuer.
    </p>
  </div>
  <div class="rg-moment-code">

```ts title="policy.ts"
// `Policy` lives in the deploy-time half of the package
import * as Ripple from "@ripple/alchemy";
import { Todo, Todos, User } from "./schema";

const P = Ripple.Policy;

export const policy = P.policy(Todos, {
  principal: User.sub,   // the token's `sub` claim
  classes: ["member"],
  ns: {
    user: { read: P.allow(P.eq(User.sub, P.claims.sub)) },
    todo: {
      read:    P.allow(P.eq(Todo.owner, P.principal)),
      create:  P.allow(P.class("member")),
      add:     P.allow(P.eq(Todo.owner, P.principal)),
      retract: P.allow(P.eq(Todo.owner, P.principal)),
      retractEntity: P.allow(P.eq(Todo.owner, P.principal)),
      // every new todo is stamped with its owner
      preset: [P.preset(Todo.owner, P.principal)],
      // narrows the namespace read: `todo/note` never leaves
      // the edge for anyone but its owner
      attrs: [P.attr(Todo.note, { read: P.allow(P.eq(Todo.owner, P.principal)) })],
    },
  },
});
```

```ts title="app.ts"
// Ada is signed in. Todo 1042 belongs to someone else.
await run(db.transact(function* (tx) {
  yield* tx.add(1042, Todo.title, "mine now");
}));

// Unauthorized — 403, code "policy", attr ":todo/title"
//   refused at the edge, before the write travels on
// TxRejected — 409, no transaction number is spent
//   refused by the writer, against the real data
```

```ts title="alchemy.run.ts"
// `pulls` are the shapes your app reads. `todo/note` has a
// narrowed read rule, so a shape asking for it as a required
// key fails here — at deploy, not on somebody's screen.
Ripple.Policy.compile(policy, { pulls: [todoShape] });
```

<h2 class="rg-h2">What you get</h2>

<div class="rg-benefits">
  <div class="rg-benefit rg-benefit--lead">
    <h3>A mistyped write does not compile</h3>
    <p>
      Names, value types, cardinality and uniqueness all come from the
      catalog, so <code>tsc</code> checks every write and every query shape
      against it. The bad write is a red squiggle, not a row in production.
    </p>
  </div>
  <div class="rg-benefit rg-benefit--lead">
    <h3>Queries update themselves</h3>
    <p>
      A standing query rides one WebSocket per page. Every write moves the
      connection forward and each standing query re-runs against the new state:
      no polling, no invalidation, no stale screen.
    </p>
  </div>
  <div class="rg-benefit">
    <h3>One database per customer, for free</h3>
    <p>
      <code>ripple.db("acme", Catalog)</code> is a pure function call — no
      create, no provisioning, no request. One deployed peer serves every name,
      each with its own writer and key prefix in storage.
      <a href="/concepts/databases-are-names/">How that works →</a>
    </p>
  </div>
  <div class="rg-benefit">
    <h3>Nothing is overwritten</h3>
    <p>
      Writes append facts, so <code>db.asOf(t)</code> reads the database as it
      was at an earlier transaction and <code>db.history</code> shows what
      changed. Reach is bounded by retained checkpoints — 20 by default, so pick
      that number deliberately; it is not "forever".
    </p>
  </div>
</div>

<h2 class="rg-h2">Instead of what?</h2>

<p class="rg-lede">
  Ripple is small and pre-release. Here is the honest trade against what you
  are probably using today.
</p>

<div class="rg-vs">
  <div class="rg-vs-row">
    <h3>Durable Objects + SQLite, or D1 + Drizzle</h3>
    <p>The same primitives, already assembled: you stop writing the live fan-out, the per-tenant routing, the migration runner and the authorization middleware, and keep the account and deploy you already have. You give up SQL and hand-tuning the storage layout.</p>
  </div>
  <div class="rg-vs-row">
    <h3>Postgres + an ORM</h3>
    <p>You keep the types and lose SQL. No migration ever rewrites old data and live queries come standard — but there is no planner to tune, no <code>psql</code>, and no joins across two databases.</p>
  </div>
  <div class="rg-vs-row">
    <h3>Convex</h3>
    <p>The same "the query re-runs itself" model, deployed into your own Cloudflare account instead of a hosted platform, and a database per customer is a function call rather than a deployment. There is no dashboard, no scheduled functions and no file storage.</p>
  </div>
  <div class="rg-vs-row">
    <h3>Supabase</h3>
    <p>Row rules are here, per attribute, deny-by-default and running at the edge, and a database per tenant costs one function call. Ripple only verifies JWTs, though: bring your own identity provider and your own file storage.</p>
  </div>
  <div class="rg-vs-row">
    <h3>Instant</h3>
    <p>The same graph-in-the-browser feel with per-user permissions, except you own the deployment end to end. Nothing is hosted for you and there is no admin console.</p>
  </div>
</div>

<div class="rg-limits">
  <strong>What Ripple does not have</strong>
  <ul>
    <li>SQL, or joins across databases</li>
    <li>An npm package — you clone the repo</li>
    <li>A hosted dashboard</li>
    <li>An identity provider of its own — bring any issuer with a JWKS endpoint</li>
  </ul>
  <p>Throughput ceiling: low thousands of writes per second, per database. Past that you split into more databases — a function call, not a deployment — and the price is the no-joins line above.</p>
</div>

<h2 class="rg-h2">How it works</h2>
<p class="rg-lede">Three parts, one deploy: one place commits writes, object storage keeps every version, reads run at the edge.</p>

<div class="rg-how">
  <div class="rg-how-box">
    <span class="rg-step">writes</span>
    <h3>One writer</h3>
    <p>Each database has exactly one thing that commits writes, in order: no write conflicts to resolve, no leader election, no "eventually".</p>
  </div>
  <div class="rg-how-box">
    <span class="rg-step">storage</span>
    <h3>Durable storage</h3>
    <p>A write is durable in the writer's own storage before your call returns. Immutable segments reach object storage afterwards and are never rewritten, which is why you can still read yesterday.</p>
  </div>
  <div class="rg-how-box">
    <span class="rg-step">reads</span>
    <h3>Readers at the edge</h3>
    <p>Queries run next to your app against copies of that storage, so reads never wait behind writes and a slow query cannot stall a commit.</p>
  </div>
</div>
