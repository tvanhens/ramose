A live query answers itself: hand it the query you would run once, and you get the rows now and the rows again every time the database changes. This page is for React developers who have run a query and want the screen to stay current.

<Learn learn={["Read a query live with useLive", "What re-runs, and when", "Where live queries work (and where they don't)"]} before={[{ href: "/guides/queries/", label: "Read data" }]} minutes={6} />

## In React

Reef's board is one **live query** — a query that re-runs itself whenever the database changes and hands your screen new rows ([glossary](/concepts/glossary/#live-query)):

```ts title="examples/reef/src/app/screens/BoardScreen.tsx#use-live-board"
  const board = useLive(db, boardQuery);
  const people = useLive(db, peopleQuery);
  const labels = useLive(db, labelsQuery);
```

`useLive(db, query)` returns `{ rows, error, ticks }`. `rows` is `undefined` until the first answer; `error` is set only when the query can never succeed (bad request, a wrong database name, no permission, memory limit); `ticks` counts **updates** ([glossary](/concepts/glossary/#tick)) — a local write applied on the overlay, or a filtered transaction arriving on the **WebSocket connection** ([glossary](/concepts/glossary/#connection)). Render with `key={row.id}`.

## See it

Open the same workspace in two windows and drag a card. The window you dragged in moves immediately; the other window follows within about a second, locally and deployed, and Reef's header pill pulses on every update (`key={ticks}` re-triggers the animation):

<Shot src="/reef/live-sync.gif" alt="Two Reef windows stacked; cards moved in the top window appear in the same columns in the bottom one, tick counters climbing" caption="Two windows on the same workspace; the live pill pulses on every update." code="examples/reef/src/app/screens/BoardScreen.tsx:260-263" />

There is no refetch code anywhere in Reef. Nothing at the write site announces the change, and there is no cache to invalidate.

## What re-runs, and when

- **After your own write** — the overlay applies it locally and the query re-runs in the window that wrote, before the HTTPS POST returns.
- **After anyone else's write.** Other windows receive a filtered transaction over their **WebSocket connection** ([glossary](/concepts/glossary/#connection)) and re-run locally. Writes always go over HTTPS. A write this caller cannot read does not arrive on the connection. If their access itself changes (they gain or lose a record), the connection says so and the next run sees the new view.
- **A re-run is a whole re-run.** No diffing: the query is evaluated again, permissions and limits applied exactly as for `db.query`.
- **Only news is emitted.** Identical results are not emitted again, so a write the query does not see is not a re-render.
- **Dropped connections recover on their own** — retries back off from 250 ms to 5 s and the connection reconnects in place.
- **A pinned view emits once and completes.** `useLive(db.asOf(t), query)` has no news to deliver; `rows` stays.

## Live reads of one record

`usePull` is the same idea for one record. Reef's issue panel keeps one open on the selected issue; every emission — an edit from any window — resets the drafts:

```ts title="examples/reef/src/app/components/IssueDetail.tsx#use-pull-extra"
  const extra = usePull(db, { id: issueId }, issueExtraShape).rows ?? null;
```

`{ id: issueId }` inline is fine — the subject is compared by value, not by identity.

## Where live queries work

A live query needs a WebSocket connection — that is how filtered transactions reach the page, and how the session hosts the overlay the query runs against.

| environment | live queries |
| --- | --- |
| a browser, through `Ramose.connect` (or `RamoseProvider`) | yes — this is the intended home |
| a Worker calling the server through `Ramose.Databases` | **no** — server-side handles have no `live` / `livePull`. See [Live queries need a browser](/guides/workers/#live-queries-need-a-browser) |
| Node or Bun | only where a global `WebSocket` exists, or one you pass to `Ramose.connect` |

### Outside React

`db.live(query)` returns a **stream** of results, not a single value, so `Effect.runPromise` cannot run it — that rule is for one-shot calls like `db.query`. Consume it with `Stream.runForEach`:

```ts title="watch.ts"
import * as Effect from "effect/Effect";
import * as Stream from "effect/Stream";

await Effect.runPromise(
  Stream.runForEach(db.live(todoQuery), (rows) =>
    Effect.sync(() => console.log(rows)),
  ),
);
```

That call runs until you interrupt it, re-emitting the whole result set on every update. In React, `useLive` does this for you.

## What it costs

There is no per-query subscription state on the server. A live query is a re-run of the same read path against the local overlay, triggered by an overlay apply or an inbound filtered transaction. Bursts of small writes coalesce, because re-runs happen per update rather than per write. Pinned `asOf` / `history` still read the server.

## Inline values

`useLive` keys its subscription on the lowered query AST, not object identity. Two components that build the same query share one subscription. Put changing values in `.where` — no bindings argument:

```ts title="examples/reef/src/app/components/IssueDetail.tsx#comments-live"
  const comments = useLive(db, commentsQuery(issueId));
```

Same `issueId` → same key → same shared subscription, even when the query object is new every render. A different `issueId` is a different AST: the hook resubscribes. That is the point. Unstable values (`where({ at: new Date() })`) churn the key every render — keep bound values stable.

`db.asOf(t)` inline is fine — views compare by value. Derived query values (`q.one()`, `q.after(cursor)`) mint a new object each call, so a new page resubscribes, which is what a new page wants. Effect users who build a stream themselves can pass it directly (`useLive(stream)`) — see [React hooks](/reference/react/).
