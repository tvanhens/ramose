Your own Worker gets a typed client bound to the Ramose server — no URL, no token to manage. This page is for anyone who has deployed once and wants server-side reads and writes.

## The smallest Worker

You declare what the Worker may do — a **capability** ([glossary](/concepts/glossary/#capability)) — and, separately, how the call travels. The **Ramose server** is the one Cloudflare Worker that serves all your databases. The `examples/kv-style` Worker binds it once at start-up:

```ts title="examples/kv-style/app.ts:28-33 · app.ts:146"
export const App = Cloudflare.Worker(
  "App",
  { main: import.meta.url },
  Effect.gen(function* () {
    // The binding *is* the client. One `Databases`, bound once at init.
    const ramose = yield* Ramose.ReadWriteDatabases(Server);
    // …
  }).pipe(Effect.provide(Ramose.ServerBinding)),
```

Inside, a request handler names a database, writes, and reads its own write back — no fetch, no connection string:

```ts title="examples/kv-style/app.ts:59-68"
        const tenant = ramose.db(tenantId, Movies);

        const { t, dbAfter } = yield* tenant.transact(function* (tx) {
          const ada = yield* tx.entity();
          yield* ada.set(User.name, "Ada");
        });
        // `dbAfter` carries the min-`t` floor, so this reads its own write
        const names = yield* dbAfter.query(
          Query.from(User).select({ name: User.name }),
        );
```

`ramose.db(name, schema)` costs nothing per request; creating a customer's database at sign-up is on [One database per customer](/guides/workspaces/#from-a-worker). The file's `effect/unstable/http` imports are Effect 4's HTTP module — the name is Effect's, not a warning about Ramose.

## What the Worker can do

| capability | your Worker gets |
| --- | --- |
| `Ramose.ReadWriteDatabases(Server)` | `q`, `pull`, `basis`, `asOf`, `history`, `principal`, `transact`, `install` |
| `Ramose.ReadDatabases(Server)` | `q`, `pull`, `basis`, `asOf`, `history` — no `transact`, `install`, or `principal` |

`live` and `livePull` are in the type of both but do not work here (see below). There is no write-only capability: a writer that cannot read cannot look anything up.

## How calls travel

| layer | how the call travels |
| --- | --- |
| `Ramose.ServerBinding` | a **service binding** — Cloudflare's Worker-to-Worker call ([glossary](/concepts/glossary/#service-binding)): no public hop, no URL. The server must be declared as a `Cloudflare.Worker`. |
| `Ramose.ServerHttp` | the server's public URL over ordinary `fetch` — also what `alchemy dev` and deploy-time actions use |

Provide one with `Effect.provide` around the whole Worker; nothing inside changes when you swap.

## Handling failures

Errors are tagged classes. On the app path, `await db.run(…)` / `db.query(…)` reject with the class itself — `try/catch` and `instanceof`. Mapping them to HTTP is `Ramose.errorToHttp`:

```ts title="examples/kv-style/app.ts"
        Effect.catch((e) => {
          const { status, body, headers } = Ramose.errorToHttp(Ramose.toDbError(e));
          return HttpServerResponse.json(body, { status, headers });
        }),
```

`errorToHttp` lives on `ramose` and `ramose/worker`, not `ramose/db` — it is an HTTP helper, not a browser export. Configuration mistakes are not in that list on purpose: a missing binding or a malformed URL fails at start-up, not on some unlucky request. `Unavailable` and `NetworkError` are tried 6 times before you see them.

## Live queries need a browser

:::caution
A **live query** re-runs itself when the database changes ([glossary](/concepts/glossary/#live-query)). `db.live` needs a WebSocket to the server, and a Worker-to-Worker binding has none. Calling it there fails outright with `ramose: db.live needs the session socket` rather than returning an error you can catch. Run live queries in the browser through `Ramose.connect`; let your Worker do request-shaped reads and writes.
:::

The complete Worker is [`examples/kv-style`](https://github.com/tvanhens/ramose/tree/master/examples/kv-style): four files, type-checked with the repo.
