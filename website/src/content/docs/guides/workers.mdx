Your own Worker gets a typed client bound to the Ramose server — no URL, no token to manage. This page is for anyone who has deployed once and wants server-side reads and writes.

## The smallest Worker

You declare a **capability** ([glossary](/concepts/glossary/#capability)); `Ramose.layer` picks how the call travels. The **Ramose server** is the one Cloudflare Worker that serves all your databases. The `examples/kv-style` Worker binds it once at start-up:

```ts title="examples/kv-style/app.ts#worker-app · examples/kv-style/app.ts#worker-layer"
export const App = Cloudflare.Worker(
  "App",
  { main: import.meta.url },
  Effect.gen(function* () {
    // The binding *is* the client. One `Databases`, bound once at init.
    const ramose = yield* Ramose.Databases(Server);

    Effect.provide(Ramose.layer),
```

Inside, a request handler names a database, writes, and reads its own write back — no fetch, no connection string:

```ts title="examples/kv-style/app.ts#tenant-transact"
        const { t, dbAfter } = yield* tenant.effect.transact(function* (tx) {
          const ada = yield* tx.entity();
          yield* ada.set(User.name, "Ada");
        });
        // `dbAfter` carries the min-`t` floor, so this reads its own write
        const names = yield* dbAfter.effect.query(namesQuery);
```

`ramose.db(name, schema)` costs nothing per request; creating a customer's database at sign-up is on [One database per customer](/guides/workspaces/#from-a-worker). The file's `effect/unstable/http` imports are Effect 4's HTTP module — the name is Effect's, not a warning about Ramose.

## What the Worker can do

| handle | your Worker gets |
| --- | --- |
| `ramose.db(name, schema)` | `q`, `pull`, `basis`, `asOf`, `history`, `principal`, `transact` / `run`, `install` |
| `Ramose.asRead(db)` | type-level read-only view of the same handle — writes still exist at runtime; policy is what enforces them |

`live` and `livePull` are **not** on this type — they are client subscriptions (`ramose/db`, `ramose/react`). There is no write-only capability: a writer that cannot read cannot look anything up.

## How calls travel

`Ramose.layer` picks the hop: a **service binding** ([glossary](/concepts/glossary/#service-binding)) when the caller is another Worker in the same stack and the binding is present, the server's public URL over `fetch` otherwise. Provide it with `Effect.provide` around the whole Worker; nothing inside changes when the wire swaps.

## Handling failures

Errors are tagged classes. On the app path, `await db.run(…)` / `db.query(…)` reject with the class itself — `try/catch` and `instanceof`. Mapping them to HTTP is `Ramose.errorToHttp`:

```ts title="examples/kv-style/app.ts#error-to-http"
        // Tagged DbError → HTTP. One helper instead of a 9-arm catchTags.
        Effect.catch((e) => {
          const { status, body, headers } = Ramose.errorToHttp(Ramose.toDbError(e));
          return HttpServerResponse.json(body, { status, headers });
        }),
```

`errorToHttp` lives on `ramose` and `ramose/worker`, not `ramose/db` — it is an HTTP helper, not a browser export. Configuration mistakes are not in that list on purpose: a missing binding or a malformed URL fails at start-up, not on some unlucky request. `Unavailable` and `NetworkError` are tried 6 times before you see them.

## Live queries need a browser

A **live query** re-runs itself when the database changes ([glossary](/concepts/glossary/#live-query)). `db.live` needs a WebSocket to the server. Server-side handles from `Ramose.Databases` do not include `live` / `livePull` — those methods are not on the type. Run live queries in the browser through `Ramose.connect`; let your Worker do request-shaped reads and writes.

The complete Worker is [`examples/kv-style`](https://github.com/tvanhens/ramose/tree/master/examples/kv-style): four files, type-checked with the repo.
