Application Workers can call Ramose through a Cloudflare service binding. The same catalogs, query language, operations, and policy apply; the binding removes public network hops, not authorization.

## Bind the service

Declare the application Worker and Ramose Server in one Alchemy stack, then provide the generated service binding through the Ramose server layer. Resolve the application catalog at module scope so query and operation types remain stable.

```ts
const app = yield* Cloudflare.Worker("Web", {
  entrypoint: import.meta.resolve("./src/worker.ts"),
  bindings: { DATA: server.binding },
})
```

Use the exact binding shape exported by your `Ramose.Server` version. Avoid rebuilding a public URL and bearer-token client inside the same Cloudflare account.

## Open a request-scoped principal

Authenticate the incoming request, derive the principal, and open its authorized root through the binding:

```ts
const rootDb = await ramose.open({ principal })
```

Do not accept an internal database id from the request. Traverse child graphs through typed, authorized parent queries just as the browser does.

## Query on the server

Server reads are request/response operations, not browser observations:

```ts
const rows = await projectDb.query(
  projectDb.query.from(Task).where(Task.done.eq(false)).page({ first: 50 }),
)
```

They execute against the server's filtered database capability and return plain data. There is no IndexedDB replica, optimistic layer, or multi-tab leader in a Worker request.

## Invoke product operations

Use the same operation definitions as the web app:

```ts
const receipt = await task.mutate.setDone({ done: true })
```

Background jobs need an explicit service principal whose grants match the job—not a universal bypass token. Record the product operation and resulting receipt so retries preserve the original invocation identity.

## Long-running workflows

One operation transacts inside one graph. For work that spans graphs or external services:

1. Commit a workflow entity and current state in its owning graph.
2. Perform one external or cross-graph step.
3. Invoke another operation to record success or a recoverable failure.
4. Resume by stable workflow identity after retries.

This makes partial progress visible and avoids claiming atomicity the platform cannot provide.

## Map errors deliberately

Translate unauthenticated and inaccessible results without leaking hidden resource existence. Treat domain operation rejection as an expected product outcome. Retry temporary availability failures with the same invocation id; do not retry invalid input, policy denial, or query budget failures unchanged.
