This page is the **schema** — your data model as one TypeScript value ([glossary](/concepts/glossary/#schema)). For anyone who has built the first app and wants to model real data.

## Three pieces, and that is the whole vocabulary

- **`Ramose.string()`** (and the other value shorthands) declare one **field** — a named, typed slot ([glossary](/concepts/glossary/#field)).
- **`Ramose.Entity`** groups fields into a **record type** — a kind of record, like a table ([glossary](/concepts/glossary/#record-type)). `Issue.title` is `:issue/title` on the wire; you always write `Issue.title`. Names match `IDENT_NAME_RE`; `id` / `ns` / `fields` / `_tag` / `traits` are reserved. `{ traits: [Taggable] }` flattens `Ramose.Trait` fields and keeps their idents.
- **`Ramose.Schema`** collects record types into the schema a database installs. The object key must be the entity's name; `Schema([User, Label])` does that for you.

## Reef's schema, annotated

Reef's whole data model is one TypeScript file. The parts that matter:

```ts title="examples/reef/src/domain/schema.ts#user-entity · examples/reef/src/domain/schema.ts#label-entity"
export const User = Ramose.Entity("user", {
  sub: Ramose.Field.unique(Ramose.string(), "upsert", {
    doc: "Better Auth user id — the JWT `sub`; the policy resolves principals through it",
  }),
  role: Ramose.string({
    doc: "Policy class, materialized by the peer from the JWT at session establishment",
  }),
  name: Ramose.string({
    optional: true,
    doc: "Display name, stamped by the peer from ramose.attrs.name",
  }),
  email: Ramose.string({
    optional: true,
    doc: "Email, stamped by the peer from ramose.attrs.email",
  }),
});

export const Label = Ramose.Entity("label", {
  name: Ramose.Field.unique(Ramose.string(), "upsert"),
  color: Ramose.string(),
});
```

```ts title="examples/reef/src/domain/schema.ts#issue-entity"
export const Issue = Ramose.Entity("issue", {
  title: Ramose.string(),
  description: Ramose.string({ optional: true }),
  status: Ramose.Enum(["backlog", "todo", "doing", "done"]),
  priority: Ramose.Enum(["none", "low", "medium", "high", "urgent"]),
  /** Fractional order inside a column; drag-and-drop writes midpoints. */
  rank: Ramose.float(),
  createdAt: Ramose.timestamp(),
  creator: Ramose.Ref(User),
  assignee: Ramose.Ref(User, { optional: true }),
  labels: Ramose.Field.many(Ramose.Ref(Label)),
  /** Admin-only field — the policy narrows its `read` (see policy.ts). */
  privateNote: Ramose.string({
    optional: true,
    doc: "visible to the owner class only",
  }),
});
```

`Comment` has the same shape, and `Reef = Ramose.Schema({ user, label, issue, comment })` collects the four.

| field | what it means |
| --- | --- |
| `user.sub` | The account id from the sign-in system. `Field.unique(…, "upsert")` = one **record** ([glossary](/concepts/glossary/#record)) per person, and you can look a user up by it. Used by permissions later. |
| `issue.status`, `issue.priority` | Closed string sets (`Ramose.Enum`) — the field carries `.members`. |
| `issue.rank` | A double (`Ramose.float()`). |
| `issue.creator` → `user` | A **reference** — a typed foreign key ([glossary](/concepts/glossary/#reference)). Permissions fill it in for you. |
| `issue.labels` → `label` | A *set* of references — no join table. |
| `issue.privateNote` | Admin-only text; the policy masks it for everyone else. |

Every record type also gets an `id` field for free (`Issue.id`).

## Value types

| shorthand | stores |
| --- | --- |
| `Ramose.string()` · `Ramose.boolean()` | text · true/false |
| `Ramose.float()` | a double (`Issue.rank`) |
| `Ramose.int()` | a whole `number`, stored as a long — it is a JavaScript number, so nothing above 2⁵³ is exact |
| `Ramose.timestamp()` | a point in time — you pass and receive a `Date` |
| `Ramose.Enum(["low", "med", "high"])` | one of those strings |
| `Ramose.Ref(User)` · `Ramose.Ref(Taggable)` · `Ramose.Ref.self` | a reference to that type · any composer of that trait · the same type |
| `Ramose.Ref(() => Other)` | the same, as a thunk — only when `Other` is declared later |
| `Ramose.uuid()` | a canonical UUID `string` |
| `Ramose.bytes()` | binary data (`Uint8Array`) |

Shorthands take the option bag (`doc`, `index`, `optional`) and compose with `Field.many` / `Field.unique` / `Field.owned`. A raw [Effect Schema](https://effect.website) is the advanced form: `Ramose.Field(schema)` — `String` / `Number` / `Boolean` infer a value type. Anything else types `valueType` as missing; wrap with `Ramose.stored(schema, vt)` or use `Ramose.Enum([...])`. Branded schemas (`Long`, `Instant`, `Uuid`, `Bytes`) stay that vocabulary — `Field(Ramose.Uuid)` rows are `string`.

## Many, unique, owned

These three are the function, not bag keys.

| constructor | effect |
| --- | --- |
| `Field.many(schema)` | **one value or many** ([glossary](/concepts/glossary/#one-or-many)): a set — a second value adds rather than replaces |
| `Field.unique(schema, "upsert")` | a **unique key** ([glossary](/concepts/glossary/#unique-key)): one record per value; `[User.sub, "…"]` looks it up; a colliding `put` [unifies](/guides/transactions/#change-fields) |
| `Field.unique(schema, "strict")` | unique, but a colliding write is rejected |
| `Field.owned(schema)` | the one declared cascade: the referenced record is deleted with its parent. Requiredness never implies this. `.reverse` is one record — a component has at most one owner |

`"upsert"` unifies on collision; `"strict"` throws (wire `:db.unique/identity` / `:db.unique/value`). They compose: `Field.many(Field.owned(Ref(Part)))`.

## Options

| option | default | effect |
| --- | --- | --- |
| `optional` | `false` | omitted at create; `| undefined` on the default row. Card-many is already an empty set and is never required. Also optional when the Effect schema admits `undefined` — say `optional: true` if you mean it. |
| `index` | true when the field is unique | keeps a value-ordered index, so you can look a record up by value |
| `doc` | none | a description stored with the field |

## References between records

`Ramose.Ref(User)` points at another record; `Ref(Taggable)` at any composer of that trait. Naming the target lets a query hop through it (`Query.follow(Issue.assignee)`) or backwards (`Query.backlink(Issue.creator)`), and lets a shape nest (`Issue.assignee.select({ … })`) or read backwards (`Issue.creator.reverse.select({ … })`). Write `Ref(() => Other)` only when the target is declared later.

## Types flow out of the schema

Nothing downstream needs a type annotation. Reef's board row is inferred:

```ts title="examples/reef/src/domain/queries.ts#board-row-type"
export type BoardRow = Ramose.Row<typeof boardQuery>;
```

`BoardRow["priority"]` is `"none" | "low" | "medium" | "high" | "urgent"`, `createdAt` a `Date`, `assignee` `{ id; name } | undefined`. Writes are checked too: `issue.set(Issue.priority, 2)` does not compile. Your UI types are your database types; they cannot drift.

## Where the schema gets installed

`ramose.db(name, Reef)` names a database without touching the network, so something must **install** the schema — an ordinary write, safe to repeat ([glossary](/concepts/glossary/#install)). Two doors.

At deploy, for a database you know up front (the todos app):

```ts title="examples/todos/resources.ts"
export const Server = Ramose.Server("Ramose", {
  databases: { todos: Todos },
});
```

From the app, for names created at runtime — how Reef makes a workspace:

```ts title="examples/reef/src/app/ramose.ts#provision-workspace"
      await ramose.db(slug, Reef).run(provisionWorkspaceOp, {});
```

Which door, and why: [One database per customer](/guides/workspaces/#two-doors-to-install-the-schema).

A database installed before required-at-transact reads every card-one field as required until `install()` runs again. Redeploy then reinstall — [Deploy](/guides/deploy/) covers it.

## The signed-in user row

The peer always writes the principal ident (`sub`). It writes `role` only when that attr exists and is string-typed. Matching `ramose.attrs` at login are per-token and never guaranteed — they do not make a required field provisionable. Any other required field — including a required non-string `role` — makes session establishment `tx/required` (409). Mark those fields `optional: true` — Reef's `User.name` / `User.email` are the example. `Ramose.policy` / `compile()` fail closed if a required field is unprovisionable.

## Changing a schema later

Adding a field or a record type is another install; the app keeps running. There is no destructive migration to fear, because Ramose never rewrites a **fact** — one statement about one record's field ([glossary](/concepts/glossary/#fact)). Old data keeps the field it was written with, reads of the past keep working, and removing a field from the schema does not delete the facts that used it.

`install()` reads the installed fields first and refuses a split: value type, one-vs-many, adding or changing a unique key, a new required field on existing rows, or tightening a ref target on existing rows (`Ref` → `Ref(Taggable)`). The failure is `IncompatibleSchema`, listing every incompatible ident. Compatible changes — a new optional field, a new record type, a `doc` edit, an optional→required flip with no rows, dropping a ref target — apply silently. An optional→required flip retracts `:db/optional`. To apply an incompatible change anyway, pass `install({ allowIncompatible: [":issue/title"] })`.

Dropping an option is quieter still: nothing goes over the wire, so the old setting stays. Under a policy, only a schema class may add a new ident. Re-installing an already-deployed schema from a member token is a silent no-op (`db.install()` is safe to run twice); a new field or record type is 403.
