Ramose deploys as a Cloudflare data plane declared in the same TypeScript stack as your application. Use separate Alchemy stages for development, preview, and production.

## Declare the resource

```ts title="alchemy.run.ts"
import * as Alchemy from "alchemy"
import * as Effect from "effect/Effect"
import * as Layer from "effect/Layer"
import * as Ramose from "ramose"
import { AppCatalog } from "./src/domain.ts"
import { auth } from "./src/auth.ts"

const program = Effect.gen(function* () {
  const server = yield* Ramose.Server("Tasks", {
    root: AppCatalog,
    auth,
    mcp: true,
  })

  return { url: server.url }
})

await Alchemy.run(program.pipe(Effect.provide(Layer.mergeAll(Ramose.layer))))
```

`Ramose.Server` owns the public Worker, graph execution, Durable Objects, object storage, synchronization, catalog installation, and optional MCP route. Keep the catalog import shared with the web application so both ends compile against the same definition identities.

## Run a local stage

```sh
bun alchemy dev
```

Local development uses the real Worker, Durable Object, object-storage, cache, WebSocket, and auth topology through Alchemy's local runtime. Give test data unique graph names instead of replacing infrastructure with in-process substitutes.

Use a non-production stage and explicit local identity configuration. Test instrumentation activates only when its flag and non-production stage guard are both present.

## Deploy a preview

```sh
bun alchemy deploy --stage preview
```

A stage is an isolated copy of compute, storage, catalogs, and secrets. Do not point a preview application at production graph storage. Set the identity provider's issuer, audience, keys, callback URLs, and allowed origins for the exact stage URL.

## Deploy production

```sh
bun alchemy deploy --stage prod
```

Catalog validation runs before incompatible definitions can reinterpret stored data. Prefer additive releases: deploy readers that tolerate both shapes, backfill, switch writers, then remove the old shape in a later release.

Production requires authentication and policy. The data plane is fail-closed when they are absent or invalid; do not add an unauthenticated fallback to make a health check pass.

## Verify the public surface

Check liveness without relying on application data:

```sh
curl https://data.example.com/health
```

Then verify with real principals:

1. An unauthenticated `/db/*` and `/mcp` request is denied.
2. A member can open only its authorized root and child paths.
3. A viewer's query cannot infer filtered fields through relationships or counts.
4. One permitted operation commits and appears in the browser replica.
5. One forbidden operation produces a rejected receipt without revealing a hidden target.
6. MCP discovery returns `describe`, `query`, and `mutate`, then an MCP mutation converges in the web app.

## Treat teardown as data deletion

Destroying a stage removes the resources Alchemy owns and may delete its graph storage. Export or preserve anything you need before teardown, confirm the exact stage name, and never use a broad production stage as a local scratch environment.
