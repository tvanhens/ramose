## What Alchemy is

Alchemy is the TypeScript deploy tool Ramose uses: one file declares your Workers and storage; `bun alchemy dev` runs it on your laptop, `bun alchemy deploy` ships it to Cloudflare. ([glossary](/concepts/glossary/#alchemy))

A **stage** is one isolated copy of the whole stack ([glossary](/concepts/glossary/#stage)): `bun alchemy deploy` ships your personal stage, `--stage prod` ships production.

## The stack file

The todos app's stack is two files. `Ramose.Server` **owns** the peer: it declares the Worker, both [Durable Objects](/concepts/glossary/#durable-object), the pinned `PEER_COMPAT` date, and the fixed `STORE` / `TRANSACTOR` / `REPLICA` bindings. You name storage and options. `databases:` seeds known catalogs at deploy. The Ramose server is the one Cloudflare Worker that serves all your databases ([glossary](/concepts/glossary/#server)). [Why these pieces exist →](/concepts/architecture/#what-runs-where)

<details>
<summary>Copy these two files as-is</summary>

```ts title="examples/todos/resources.ts"
import * as Ramose from "ramose";
import { Todos } from "./schema.ts";

export const Server = Ramose.Server("Ramose", {
  main: import.meta.resolve("./peer.ts"),
  databases: { todos: Todos },
});
```

Omit `main` to use `ramose/worker`. An explicit `worker:` is the escape hatch (extra bindings, a user-owned entry) and is validated at deploy — a typo'd Durable Object `className` or a bare `main: "ramose/worker"` fails the deploy instead of passing `/health` and dying on the first write. [Getting started](/getting-started/quickstart/) sets it up.

```ts title="examples/todos/alchemy.run.ts"
import * as Ramose from "ramose";
import * as Alchemy from "alchemy";
import * as Cloudflare from "alchemy/Cloudflare";
import * as Command from "alchemy/Command";
import * as Effect from "effect/Effect";
import * as Layer from "effect/Layer";
import { Server } from "./resources.ts";

// …
export default Alchemy.Stack(
  // …
  "ramose-todos",
  {
    providers: Layer.mergeAll(
      Cloudflare.providers(),
      Ramose.providers(),
      Command.providers(),
    ),
    state: Alchemy.localState(),
  },
  Effect.gen(function* () {
    const server = yield* Server;
    const ui = yield* Ui;
    return { peerUrl: server.url, uiUrl: ui.url };
  }),
);
```

The elided `Ui` resource starts Vite under `alchemy dev` only. `state: Alchemy.localState()` keeps deploy state on disk; the repo's root stack switches to `Cloudflare.state()` when `ALCHEMY_STATE` is not `local`.

</details>

`Ramose.Server` resolves the Worker's URL and, on a real deploy, waits until `GET /health` answers, then seeds each `databases:` catalog. Standalone `Ramose.Database` remains for runtime-provisioned multi-tenant names (Reef). Reef has no `databases:` and no `Ramose.Database` at all: its databases are created by users ([One database per customer](/guides/workspaces/#two-doors-to-install-the-schema)).

## Commands

| command | what it does |
| --- | --- |
| `bun alchemy dev <stack>` | runs the stack on your laptop in the local Cloudflare emulator (bucket and both Durable Objects included) |
| `bun alchemy deploy <stack>` | deploys your personal stage |
| `bun alchemy deploy <stack> --stage prod` | deploys production |
| `bun alchemy destroy <stack>` | tears a stage down — see [Tearing down](#tearing-down) |

The stack argument is the file, for example `examples/todos/alchemy.run.ts`.

## Credentials

| name | purpose |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | Workers Scripts Write (covers Durable Objects), Workers R2 Storage Write, Account Settings Read |
| `CLOUDFLARE_ACCOUNT_ID` | the account to deploy into |

Local `alchemy dev` needs neither for real. Put placeholders in `.env` (`CI=1`, a 32-hex `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN=x`) or use this repository's `bun run dev:todos` / `bun run dev:reef`, which set the same keys. `ALCHEMY_STATE` is not a credential — only set it when you mean the stack to use a local file store.

## Deploy Reef

Reef's UI is served by its auth Worker, so it deploys in two passes with a build between them:

```sh frame="terminal"
bun alchemy deploy examples/reef/alchemy.run.ts          # first pass: the Workers, the R2 bucket, and Better Auth's D1 database
VITE_RAMOSE_URL=<peerUrl> bunx vite build examples/reef  # bake the peer URL into the SPA
bun alchemy deploy examples/reef/alchemy.run.ts          # second pass: ship the assets
```

The API token also needs `Account / D1 / Edit` for Better Auth's database.

## Auth at deploy

:::caution[A new server is open to everyone]
Until you add a policy there is no authentication: every caller has full rights on every database. Set one before you point real users at a deployed server, and walk [Before production](/guides/before-production/) first.
:::

Pass `auth` on the owned Server — it is applied onto the Worker's env, and a policy with no `jwksUrl`, `issuers`, or `aud` fails the deploy instead of denying every request at run time:

```ts title="alchemy.run.ts"
export const Server = Ramose.Server("Ramose", {
  databases: { todos: Todos },
  auth: {
    policy: process.env.RAMOSE_POLICY, // Ramose.Policy.compile(policy, { pulls })
    jwt: AUTH, // { issuer, audience, ttl } — fills issuers / aud / maxTtl
    jwksUrl: process.env.RAMOSE_JWKS_URL,
    allowedOrigins: process.env.RAMOSE_ALLOWED_ORIGINS,
  },
});
```

On the explicit-Worker hatch, set the matching `RAMOSE_*` keys on the Worker yourself; `auth` on Server is then the deploy-time check only. Reef's real wiring is on [Sign in and roles](/guides/sign-in/#wire-the-server).

## Tearing down

:::caution
`alchemy destroy` deletes the stack's R2 bucket and Durable Object classes — your data goes with them. Only the `Ramose.*` resources are no-ops. Back up first.
:::

## Reference: the Ramose resources

`ramose` re-exports all of `ramose/db` and adds these. Import it as `* as Ramose`.

| name | what it is |
| --- | --- |
| `Ramose.Server(id, props)` | owns the peer (or validates an explicit `worker:` hatch). Props: `databases?` (catalog seeder), `storage?`, `main?`, `env?`, `name?`, `dev?`, `peer?`, `worker?` (hatch), `url?`, `token?`, `auth?` (`policy`, `jwt`, `jwksUrl`, …), `probe?`. Outputs `{ url, workerName, token, seeded }`. Delete is a no-op. |
| `Ramose.Database(id, props)` | standalone catalog install for runtime-provisioned names (Reef). Props: `server`, `schema`, `name?`. Outputs `{ name, server, t }`. Known catalogs belong on `Server({ databases })`. |
| `Ramose.Databases(server)` | the **capability** ([glossary](/concepts/glossary/#capability)): a server-side client (`q`, `transact` / `run`, `install` — no `live` / `livePull`). Read-only is `Ramose.asRead(db)`. |
| `Ramose.layer` | one transport: service binding when the host Worker has one, HTTPS otherwise |
| `Ramose.providers()` | merge into your stack's `providers` next to `Cloudflare.providers()` |
| `Ramose.PEER_COMPAT` | the one compat date + `nodejs_compat` every peer Worker is deployed with |

Using a capability inside a Worker is on [Use it from a Worker](/guides/workers/).
