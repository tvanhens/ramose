A subgraph is a child database reached through a parent Graph row. Use one when the boundary improves ownership, authorization, lifecycle, offline footprint, or write distribution enough to justify cross-graph coordination.

## Use one graph by default

Keep entities together when they are queried together, changed atomically, and share one ownership and lifecycle boundary. Ordinary references and nested projections are cheaper than graph traversal. A small product may need only its root forever.

## Promote a container to a subgraph when

- nearly every write belongs to one organization, project, notebook, world, room, or device;
- access to the container should gate all descendants;
- the container can be archived, retained, exported, or evicted as a unit;
- its data should synchronize only after a user opens it;
- independent containers should write in parallel;
- its domain needs a different schema or policy.

Avoid a subgraph when common screens join across the proposed boundary, one user action must commit on both sides, or every active session would open thousands of tiny children.

## Define the child catalog first

```ts
const ProjectSchema = Ramose.Schema({ task: Task, member: Member })

export const ProjectCatalog = Ramose.Catalog("project-v1", {
  schema: ProjectSchema,
  policy: projectPolicy,
})
```

The catalog definition is reusable code. Creating a Project graph does not clone or modify it.

## Bind a parent entity to the child

```ts
export const Project = Ramose.Entity(
  "project",
  { title: Ramose.string() },
  {
    traits: [Ramose.Graph(ProjectCatalog)],
    operations: (Operation) => ({
      createProject: Operation({
        self: false,
        input: S.Struct({ name: S.String, title: S.String }),
        output: S.Struct({ id: Ramose.EntityId }),
        run(op, input) {
          const project = op.create({
            name: input.name,
            title: input.title,
          })
          return { id: project }
        },
      }),
    }),
  },
)
```

The operation creates the Graph row and any related parent facts atomically. Ramose applies the fixed catalog binding; callers cannot supply or change it. Names are unique among siblings.

## Open a child in the application

```ts
const projectDb = organizationDb.query
  .from(Project)
  .where({ name: projectName })
  .one()
  .db()

const tasks = useQuery(projectDb.query.from(Task))
```

The handle is inert until observed. Zero or hidden matches produce no child; several matches are rejected. Each path segment is resolved through the parent's authorized value, and the child policy is applied independently.

## Open a child through MCP

`describe` returns visible Graph cards with derived paths. Agents pass the returned path to later tools:

```json
{ "at": ["acme", "launch"], "browse": { "kinds": ["operation"] } }
```

Paths are root-relative. The client never sends a database id or catalog key.

## Design cross-graph workflows explicitly

There are no cross-graph joins or transactions. Put the command on the graph that owns the invariant. When another graph needs a summary, copy a minimal projection with its source identity and version, then make reconciliation visible and retryable.

Examples: keep organization membership in the organization graph and project work in each project graph; keep a project card in the organization as a directory summary; do not duplicate every task upward.

## Measure the boundary

For each candidate, estimate active graph size, cold snapshot size, mutation rate, concurrent writers, child count opened per session, and workflows that cross the line. A boundary that reduces one hot graph into many naturally owned graphs is valuable. A boundary that only mirrors route structure usually is not.
