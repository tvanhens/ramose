A child graph is a real database boundary. It buys isolation and independent lifecycle, but it also ends joins and transactions and creates another replica to activate. Use that trade deliberately.

<Learn learn={["The signals that justify a child graph", "The costs created by every boundary", "How to review a proposed hierarchy before committing"]} before={[{ href: "/concepts/graph-of-graphs/", label: "Graph of graphs" }]} minutes={10} />

## Strong reasons to split

Create a child graph when one or more of these are central to the product:

- **Authorization:** membership or roles are naturally scoped to a tenant, workspace, project, or private room.
- **Lifecycle:** the unit should archive, export, delete, restore, or move independently.
- **Isolation:** a noisy or large tenant should not shape every other tenant's query and synchronization cost.
- **Locality:** most reads and writes stay within the unit.
- **Delegation:** a parent should enumerate and authorize children without owning their full contents.

A project with its own members, tasks, comments, audit history, and archive lifecycle is a good candidate. A task's checklist is usually not.

## Weak reasons to split

Do not create a graph merely because:

- An entity has many related records.
- The UI has a nested route or navigation panel.
- A table might become large.
- You want a namespace for type names.
- One screen should load lazily.

Relationships, filters, and client activation already solve those problems without giving up cross-entity queries and transactions.

## Price the boundary

Each active graph has a separate local replica, synchronization cursor, policy projection, outbox coordination, and server execution context. The fixed cost is often more important than entity count.

Each boundary also creates semantic constraints:

- Queries cannot join across graphs.
- Operations cannot transact across graphs.
- Parent summaries must be explicitly maintained or queried per child.
- Moving data between graphs becomes a workflow with intermediate states.
- Paths must be authorized segment by segment.

Thousands of dormant child graphs are fine; thousands activated in one session are not. Route and component structure should activate only the user's current working set.

## Keep root graphs small

The root is a directory and control plane, not a warehouse for every tenant's data. Keep identities, memberships, child graph entries, and small global configuration there. Put high-volume operational data in the child that owns it.

If the home screen needs aggregate counts across many children, maintain a bounded summary in the parent through an explicit workflow. Do not open every child graph on page load.

## Choose path segments for people

Graph paths are public, human-facing navigation—not storage identity. A mutable project slug may be a path segment because Ramose resolves it to a stable internal identity. Renaming it changes navigation without orphaning the database.

Avoid secrets in paths. Authorization protects every segment, but URLs, logs, and history may still contain public path text.

## Review with a boundary brief

For every proposed child graph, document:

1. What gets isolated and why?
2. Who can discover and enter it?
3. What is its independent lifecycle?
4. Which common question now crosses the boundary?
5. Which action now needs a multi-step workflow?
6. How many graphs will a normal session activate?
7. What bounded summary, if any, belongs in the parent?

If the answers are vague, keep the data together until a concrete boundary emerges.
