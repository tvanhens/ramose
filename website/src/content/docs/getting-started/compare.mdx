Ramose is closest to an offline-first application database, a multi-tenant graph store, and an agent backend combined. Its differentiator is not one isolated feature: the local client, nested graph boundaries, policy, operations, and MCP surface are one model.

## The short version

| If you would otherwise use | Ramose feels familiar because | The decisive difference |
| --- | --- | --- |
| Convex | typed queries and server-controlled functions | complete offline replicas, graph boundaries, your Cloudflare account, native MCP |
| Instant or Firebase | local-first reads and realtime synchronization | code-defined operations and policy, nested databases, no hosted control plane |
| Supabase | the database enforces access | field-level filtered views and operation grants apply to app and agent callers |
| D1 + Drizzle | it runs on Cloudflare primitives | sync, history, authorization, graph routing, and MCP are already assembled |
| Postgres + an ORM | types flow from a schema | no SQL, no cross-graph joins, immutable history, offline query execution |

## Choose Ramose when boundaries matter

The graph-of-graphs model is unusually good for products whose natural containers should also be isolation and scale boundaries: organizations, projects, notebooks, worlds, repositories, rooms, or devices. Each child graph can have its own catalog and policy while still being reached through an authorized parent path.

## Choose something else when SQL is the product

Ramose does not provide ad-hoc SQL, arbitrary cross-graph joins, a BI ecosystem, full-text search, or a managed console. If analysts need to explore the primary store directly, Postgres or a warehouse is usually the better center of gravity. Ramose data can still feed an analytical system.

## The performance trade

Writes inside one graph are committed in order by one authoritative writer. That gives each graph simple ordering, uniqueness, receipts, and history. It also gives each graph a finite write ceiling. Scale writes by choosing graph boundaries that distribute ownership; do not expect one hot graph to scale horizontally without changing semantics.

Queries run over a complete authorized local graph in the browser and over immutable filtered values on the server. They are fast when a graph is appropriately sized and queries constrain indexed fields early. A giant graph increases initial sync, browser storage, local index, and query costs.

## The maturity trade

Ramose is pre-release. APIs are intentionally changing toward the coherent model documented here. There is no hosted service, support contract, dashboard, migration framework, or broad integration catalog. In return, the whole data plane runs in your account and the application model remains ordinary TypeScript.
