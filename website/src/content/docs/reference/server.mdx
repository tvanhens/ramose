`Ramose.Server` provisions the Cloudflare data plane for one application: the public Worker, authoritative graph writers, query execution, object storage, synchronization, optional MCP endpoint, and test-gated instrumentation.

*New here? Start with [Deploy Ramose](/guides/deploy/).*

## Resource declaration

```ts
import * as Ramose from "ramose"

export const data = Ramose.Server("Tasks", {
  root: AppCatalog,
  auth,
  mcp: true,
})
```

The resource owns platform bindings and compatibility configuration. Application code supplies catalogs, compiled policy, identity configuration, routes, budgets, retention, and optional observability settings.

## Public routes

| Route | Purpose |
| --- | --- |
| `GET /health` | Unauthenticated liveness without catalog or data disclosure |
| `/db/*` | Authorized browser and server data plane |
| `POST /mcp` | Optional Streamable HTTP MCP endpoint |
| OAuth metadata routes | Protected-resource and authorization discovery for MCP clients |

Database and catalog internal identifiers are never public selectors. Requests derive an authorized root from identity and traverse child graphs through public, authorized paths.

## Graph runtime

Each graph has one authoritative commit order and independently scalable read/synchronization state. Storage identity is stable even when a graph's public path changes. A graph archive changes lifecycle state without reusing its identity for another child.

Queries and operations remain inside one graph. Multi-graph workflows must make intermediate states and recovery explicit.

## Catalog installation

Deployment validates definition identities, stored value representations, trait conformance, graph bindings, operation schemas, and compiled policy. Incompatible catalog changes fail before they can reinterpret existing data.

Use staged additive changes and explicit migrations. Offline replicas and old clients may reconnect after a deployment, so compatibility is a protocol concern as well as a storage concern.

## Synchronization

The browser restores a persistent snapshot, resumes from its durable cursor, and receives authorized changes. If incremental history is unavailable or authorization changes invalidate the view, the server issues a safe resnapshot path. Clients never merge facts from a different principal or graph identity.

## MCP

With `mcp: true`, the same catalog, policy, query runtime, graph resolver, and operations back `describe`, `query`, and `mutate`. Configure OAuth metadata and query/discovery budgets before exposing the endpoint publicly.

## Test hooks

Integration instrumentation is inert unless both `RAMOSE_TEST_HOOKS=1` and a non-production stage are present. Production must fail closed even if one guard is misconfigured. Test routes are not part of the public API.

## Observability

Collect health, request latency, graph activation, snapshot size, resume/resnapshot frequency, query budget failures, operation receipt outcomes, storage faults, and synchronization lag. Correlate requests and receipts with opaque safe identifiers; redact tokens and application payloads.

## Limits and retention

Set explicit limits for query work, projection width, recursion, pages, discovery, snapshot size, retained history, queued invocations, and request bodies. Defaults should protect a multi-tenant deployment; raise a limit only with measured workload evidence.
