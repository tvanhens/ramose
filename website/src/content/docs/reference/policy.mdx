The exact rules language and token contract. This page is for people who have read [Permissions](/guides/permissions/) and [Sign in and roles](/guides/sign-in/) and want every operation, arm and claim spelled out. Rules are enforced by the Ramose server, never by the client. The **Ramose server** is the one Cloudflare Worker that serves all your databases.

*New here? Start with [Getting started](/getting-started/quickstart/).*

## Shape of a policy

`Ramose.policy` is deploy-side: import it from `ramose`, not `ramose/db`. The **policy** ([glossary](/concepts/glossary/#policy)) is one value, head/body shaped like `Query.q`. The head's `principal` attr derives `me`; every arm is a fragment (or `true`, or an OR of fragments) contextually checked against that token.

```ts
const policy = Ramose.policy(
  {
    schema: Schema,
    principal: User.sub,          // the field whose value is the token's `sub`
    classes: ["admin", "member", "viewer"],
    claims?: Schema.Struct({ … }), // shape of `ramose.attrs`, if you use it
  },
  {
    issue: { read, create, set, remove, delete, preset?, attrs? },
  },
);
```

```ts title="examples/reef/src/domain/policy.ts#own-rules"
const ownIssue = (me: Ramose.Policy.Me<typeof User>) => Query.is(Issue.creator, me);
const ownComment = (me: Ramose.Policy.Me<typeof User>) => Query.is(Comment.author, me);
```

```ts title="examples/reef/src/domain/policy.ts#policy"
export const policy = Ramose.policy(
  {
    schema: Reef,
    principal: User.sub,
    classes: CLASSES,
    claims: Schema.Struct({
      name: Schema.optional(Schema.String),
      email: Schema.optional(Schema.String),
    }),
  },
  {
    user: {
      read: true,
      // The peer upserts `sub`, `role`, and `ramose.attrs` (name, email).
      // Clients never write this row.
    },
    label: {
      read: true,
      create: P.class("member"),
    },
    issue: {
      read: true,
      create: P.class("member"),
      set: { class: "member", rule: ownIssue },
      remove: { class: "member", rule: ownIssue },
      delete: { class: "member", rule: ownIssue },
      preset: [P.preset(Issue.creator, P.principal)],
      attrs: [
        // Narrows the namespace `read`: members and viewers never see this
        // datom — pulls must ask for it as `.optional` (compile() checks).
        P.field(Issue.privateNote, { read: P.class("admin") }),
      ],
    },
    comment: {
      read: true,
      create: P.class("member"),
      remove: { class: "member", rule: ownComment },
      delete: { class: "member", rule: ownComment },
      preset: [P.preset(Comment.author, P.principal)],
    },
  },
);
```

- `principal` — the **signed-in user** is the record whose `principal` field equals the token's `sub` ([glossary](/concepts/glossary/#signed-in-user)). In an arm, `me` is that record, fully typed, no annotation.
- `classes` — the **roles** a token may carry ([glossary](/concepts/glossary/#role)); `P.class` is a claims gate in front of an arm, not an expression.
- The second argument is one block per record type, keyed as in the schema. A record type or operation with no rule **denies**.

`Ramose.policy` throws at deploy on an unknown field, class or record type, an empty or duplicate class list, a `principal` outside the schema, or a rule body the query validator rejects.

Standalone rules annotate `me` once (`(me: Ramose.Policy.Me<typeof User>) => …`), which they need anyway for reuse in app queries. Inline arms write `(me) => …` with `me` fully typed.

## Operations

| operation | when it is checked |
| --- | --- |
| `read` | every query, pull and live query — including `asOf` and `history` views |
| `create` | the first `set` to a record that has no facts yet |
| `set` | writing a value to a field of an existing record |
| `remove` | clearing a value from a field |
| `delete` | deleting a whole record |

```ts
issue: { read: true, create: P.class("member"), set: { class: "member", rule: ownIssue } }
```

Each takes one arm or a list (OR). An arm is a fragment, an array of fragments, `true`, or a class gate.

## Arms are fragments

| arm | true when |
| --- | --- |
| `true` | always — the empty fragment, public |
| `(me) => Query.is(attr, me)` | the record's `attr` equals the caller; on a many-valued field, contains them |
| `(me) => function* (e) { … }` | the fragment matches with focus `e` and principal `me` |
| `[(me) => a, (me) => b]` | any one fragment matches |
| `P.class("member")` | the caller's role is `member` (must be in `classes`) |
| `{ class: "member", rule: frag }` | the class gate holds **and** the fragment matches |

```ts
// doc → project → org → members contains the caller
const inOrg = (me: Ramose.Policy.Me<typeof User>) =>
  function* (doc) {
    const project = yield* Query.follow(Doc.project)(doc);
    const org = yield* Query.follow(Project.org)(project);
    yield* Query.is(Org.members, me)(org);
  };

const mine = (me: Ramose.Policy.Me<typeof User>) => Query.is(Doc.owner, me);
```

The same `inOrg` value pipes in the app (`pipe(entities(Doc), Query.refine(inOrg(me)))`) and installs as the policy arm — UI filtering and enforcement cannot drift.

Membership, ownership and sharing are facts in the database, not claims in the token. Revoking access is a write; it takes effect on the next version. Relation-based visibility ("issues in a project whose team I belong to") is an ordinary fragment: there is no depth cap and no second language.

`P.class` is a residual JWT claims gate, checked before the rule runs. It composes with fragments (`{ class: "member", rule: ownIssue }`) and never grows expressions. Prefer a role fact when the peer writes one (`Q.fact(me, User.role, "admin")`); keep `P.class` for deployments where the role must stay token-only.

## How rules combine

| situation | verdict |
| --- | --- |
| no rule for this record type and operation | **denied** |
| one allow arm holds | allowed |
| several allow arms, any one holds | allowed |
| a field rule and its record-type rule | both must allow — the field rule only narrows |

```ts
// 1. no rule at all for doc → nothing about a document is readable
{}
// 2. one arm: the owner may read their own documents
{ doc: { read: (me) => Query.is(Doc.owner, me) } }
// 3. two arms: the owner *or* anyone in the document's org may read it
{ doc: { read: [mine, inOrg] } }
// 4. narrowed: everything above, except doc.audit, which is admins only
{ doc: { read: [mine, inOrg],
         attrs: [P.field(Doc.audit, { read: P.class("admin") })] } }
```

## preset

`P.preset(attr, P.principal | P.claim.x)` — a **server-filled field** ([glossary](/concepts/glossary/#preset)): on `create` the server sets it from the caller. A client value identical to the preset is a no-op; a different one is refused with `Unauthorized`. The operand is `P.principal` or a claim, never a literal.

```ts title="examples/reef/src/domain/policy.ts#policy-preset"
      preset: [P.preset(Issue.creator, P.principal)],
```

## Field rules narrow

`P.field(field, rules)` sits under its own record type and can only tighten the record-type rule. A field you add later inherits the record-type rule instead of becoming world-readable.

```ts title="examples/reef/src/domain/policy.ts#policy-private-note"
        P.field(Issue.privateNote, { read: P.class("admin") }),
```

## admin and anonymous

| class | meaning |
| --- | --- |
| `admin` | skips every rule — reads unfiltered, writes unchecked; the only class that may install schema, call `explain`, or `/admin/*` routes |
| `anonymous` | given to a caller with no token, **only if the policy declares it**; otherwise token-less calls are `Unauthorized` |
| `$token` | the `RAMOSE_TOKEN` holder under a policy; cannot be declared, so no rule admits it |

:::caution
`admin` bypasses everything, including field masks. Mint it only for people who should see all of a database. `anonymous` opens the door to the internet; declare it on purpose.
:::

## Where the checks run

- **Reads are filtered, never rejected.** The server hides the facts you may not read; a list is shorter, a hidden required field makes `pull` return `null` — the same as a missing record. A fragment arm runs as one query-engine query over the *unfiltered* data, always at the *current* version, so reading the past cannot revive a revoked grant. For a named rule the engine first asks for every `e` visible to `me` and the per-fact check is a set lookup; a set that is too large falls back to one query per entity. A rule that blows the query memory budget is a 413 `policy/budget-exceeded`, not an empty result. The live connection follows the same rule: a write you cannot read never appears on it, and a grant or revoke that changes what you can see asks the page to reload its view.
- **Writes are checked twice.** Both checks run the same expansion first — implied retracts and `retractEntity` closure — and judge every fact that comes out, server-filled fields included. At the server's edge first, against a read copy that may lag: a refusal there is `Unauthorized` 403 with `code: "policy"` and the field name. Then inside the **writer**, against the writer's own current data: a refusal there is `TxRejected` 409, and no version number is used. (The writer is the one thing per database that commits writes — [glossary](/concepts/glossary/#writer).)
- **The writer's check is the authority.** Because the edge reads a copy that lags the writer, it is best-effort in *both* directions: it can refuse a write the writer would allow, and it can let one through that the writer then refuses. Handle both `Unauthorized` and `TxRejected`.
- **Refusals do not leak values.** A refused write names the field and a code, never a value.
- **The server fails closed.** A malformed policy, or a policy without a working verifier, denies every `/db/*` request and logs once at start-up.

## compile and the pulls check

`P.compile(policy, { pulls? }): string` turns the policy into the JSON `RAMOSE_POLICY` holds. Each fragment arm is promoted to a named query rule (`Query.rule` — return-var-into-head) and written into a `rules` section next to the surviving arms. Rule bodies are validated against the catalog through the query validator (attrs exist, namespaces line up). The wire version is 2; installed policies recompile at deploy.

Pass the shapes your screens read and a masked field pulled as *required* fails the deploy; without `pulls` the check is skipped. `P.checkPulls(policy, pulls)` runs the check alone.

```ts title="examples/reef/src/domain/policy.ts#compiled-policy"
export const compiledPolicy = (): string =>
  P.compile(policy, { pulls: allShapes });
```

## The token the server verifies

```json
{
  "iss": "reef-demo-auth",
  "aud": "ramose:reef",
  "sub": "user_01HQ8ZK",
  "iat": 1755499100,
  "exp": 1755500000,
  "ramose": { "db": "coral-team", "class": "member", "attrs": { "org": "org_42" } }
}
```

| claim | rule |
| --- | --- |
| `iss` | in `RAMOSE_JWT_ISS` (comma-separated list) |
| `aud` | equals `RAMOSE_JWT_AUD` |
| `exp` | required; `exp - iat ≤ RAMOSE_JWT_MAX_TTL` (default 900 s) |
| `sub` | non-empty; matched to the `principal` field |
| `ramose.db` | equals the database in the URL — else `Unauthorized` "token is not valid for this database" |
| `ramose.class` | a class the policy declares |
| `ramose.attrs` | optional; your own claims, readable as `P.claim.attrs.<key>` on a preset |

Signatures: `RS256`, `ES256` or `EdDSA`, keys from `RAMOSE_JWKS_URL` (or `RAMOSE_JWKS_JSON`). Sent as `Authorization: Bearer …`, or `?token=` on the WebSocket upgrade. Ramose verifies tokens; it never issues them — see [Sign in and roles](/guides/sign-in/#what-the-token-carries) for minting with `Ramose.claims` and `ramose/better-auth`.

```ts
Ramose.claims(auth, { sub, db, class, attrs? }, compiledPolicy?)  // → the payload above; sign it yourself
```

## Server env keys

Set `auth: { policy, jwt, jwksUrl, … }` and `token` on `Ramose.Server`. That is the source of truth; Server writes these keys onto the Worker. Do not also hand-copy `RAMOSE_*` onto a Worker env.

```ts title="examples/reef/src/infra/resources.ts"
export const Server = Ramose.Server("Ramose", {
  env: { AUTH: Api },
  auth: {
    policy: compiledPolicy(),
    jwt: REEF_AUTH,
    jwksService: "AUTH",
    jwksUrl: /* Output over the auth Worker */,
    allowedOrigins: /* Output over the SPA origin */,
  },
});
```

| key | env var | meaning |
| --- | --- | --- |
| `token` (Server prop) | `RAMOSE_TOKEN` | shared bearer; owned form binds it |
| `policy` | `RAMOSE_POLICY` | the compiled JSON; setting it arms enforcement |
| `jwksUrl` | `RAMOSE_JWKS_URL` | where the sign-in provider publishes its public keys |
| `jwksService` | `RAMOSE_JWKS_SERVICE` | service binding to fetch `jwksUrl` through; needed when the provider is a Worker on your account ([Server](/reference/server/)) |
| `issuers` | `RAMOSE_JWT_ISS` | accepted `iss` values |
| `aud` | `RAMOSE_JWT_AUD` | the required `aud` |
| `maxTtl` | `RAMOSE_JWT_MAX_TTL` | cap on token lifetime, seconds (default 900) |
| `allowedOrigins` | `RAMOSE_ALLOWED_ORIGINS` | CORS list; honoured only once a policy is set |
| `internalSecret` | `RAMOSE_INTERNAL_SECRET` | Worker-to-writer gate; minted for you when unset and a policy is set |
| `writes` (Server prop) | `RAMOSE_WRITES` | `"operations"` (default) closes raw `/transact` for app-class tokens; `"all"` is the opt-out. See [The server](/reference/server/) |

`jwt: { issuer, audience, ttl }` fills `issuers`, `aud` and `maxTtl` from one value. Which mode a server runs in — open, shared token, or policy — is decided by `RAMOSE_POLICY` and `RAMOSE_TOKEN`: see [The three server modes](/guides/permissions/#the-three-server-modes).

## Testing without a login provider

`RAMOSE_JWKS_JSON` takes a literal key set instead of a URL, so a local server can verify tokens you sign yourself.

<details>
<summary>Sign your own tokens with jose</summary>

```ts title="scripts/local-jwt.ts"
import { SignJWT, exportJWK, generateKeyPair } from "jose";

const { privateKey, publicKey } = await generateKeyPair("ES256", { extractable: true });

// 1. the server's verifier — set this as RAMOSE_JWKS_JSON
console.log(JSON.stringify({
  keys: [{ ...(await exportJWK(publicKey)), alg: "ES256", kid: "local" }],
}));

// 2. a token for one user of one database
console.log(
  await new SignJWT({ ramose: { db: "todos", class: "member" } })
    .setProtectedHeader({ alg: "ES256", kid: "local" })
    .setIssuer("https://local.test")
    .setAudience("ramose:local")
    .setSubject("user_ada")
    .setIssuedAt()
    .setExpirationTime("5m")
    .sign(privateKey),
);
```

Then on the owned Server: `auth: { policy, issuers: "https://local.test", aud: "ramose:local" }` plus `env: { RAMOSE_JWKS_JSON: process.env.RAMOSE_JWKS_JSON }`. Run `bun alchemy dev` with `RAMOSE_JWKS_JSON` set to line 1 of the script's output, and hand line 2 to the client as `Ramose.token.static(token)`. Generate both once — every run mints a fresh key pair. Reef does not need this: its Better Auth Worker signs tokens locally.

</details>

## Limits

- One policy per deployed server, over one schema; no per-database variants.
- No cross-database rules.
- 413 bodies (`clause`, `cells`, `limit`, `spentBy`) and the `x-ramose-*` timing headers are not policy-filtered. `spentBy` is `policy` when a conjoined visibility rule spent the budget, `caller` otherwise.
- Reads conjoin each namespace rule into the query before planning (a two-view join: the rule reads the unfiltered db, the caller's clauses the filtered view). `FilteredDb` remains the backstop for pull, history, raw fact access, and attribute-level narrowing.
