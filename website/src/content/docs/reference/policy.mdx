The exact rules language and token contract. This page is for people who have read [Permissions](/guides/permissions/) and [Sign in and roles](/guides/sign-in/) and want every arm and claim spelled out. Rules are enforced by the Ramose server, never by the client. The **Ramose server** is the one Cloudflare Worker that serves all your databases.

**Reads are per-fact masks. Writes are per-operation arms.** A namespace `read` (and optional attribute `read`) hides facts; a named operation's arm decides who may run that write. There is no fact write vocabulary on the public policy surface.

*New here? Start with [Getting started](/getting-started/quickstart/).*

## Shape of a policy

`Ramose.policy` is deploy-side: import it from `ramose`, not `ramose/db`. The **policy** ([glossary](/concepts/glossary/#policy)) is one value, head/body shaped like `Query.q`. The head's `principal` attr derives `me`; every arm is a fragment (or `true`, or an OR of fragments) contextually checked against that token. Pass the app's operations registry on the head so the body's `operations:` keys are the registry bindings — no string op names in app code.

```ts
const policy = Ramose.policy(
  {
    schema: Schema,
    principal: User.sub,          // the field whose value is the token's `sub`
    classes: ["owner", "member", "viewer"],
    schemaClasses: ["owner"],
    operations,                   // the app's defineOperations registry
    superuser?: "operator",
    claims?: Schema.Struct({ … }), // shape of `ramose.attrs`, if you use it
  },
  {
    issue: { read, attrs? },
    operations: { createIssueOp, setTitleOp, … },
  },
);
```

```ts title="examples/reef/src/domain/policy.ts#own-rules"
const ownIssue = (me: Ramose.Policy.Me<typeof User>) => Query.is(Issue.creator, me);
const ownComment = (me: Ramose.Policy.Me<typeof User>) => Query.is(Comment.author, me);
```

```ts title="examples/reef/src/domain/policy.ts#policy"
export const policy = Ramose.policy(
  {
    schema: Reef,
    principal: User.sub,
    classes: ["owner", "member", "viewer"],
    schemaClasses: ["owner"],
    operations,
    claims: Schema.Struct({
      name: Schema.optional(Schema.String),
      email: Schema.optional(Schema.String),
    }),
  },
  {
    user: {
      read: true,
      // The peer upserts `sub`, `role`, and `ramose.attrs` (name, email).
      // Clients never write this row.
    },
    label: {
      read: true,
    },
    issue: {
      read: true,
      attrs: [
        // Narrows the namespace `read`: members and viewers never see this
        // datom — pulls must ask for it as `.optional` (compile() checks).
        P.field(Issue.privateNote, { read: P.class("owner") }),
      ],
    },
    comment: {
      read: true,
    },
    operations: {
      provisionWorkspaceOp: P.class("owner"),
      createIssueOp: P.class("owner", "member"),
      seedSampleIssuesOp: P.class("owner", "member"),
      moveIssueOp: { class: ["owner", "member"], rule: ownIssue },
      setTitleOp: { class: ["owner", "member"], rule: ownIssue },
      setPrivateNoteOp: P.class("owner"),
      deleteCommentOp: { class: ["owner", "member"], rule: ownComment },
    },
  },
);
```

- `principal` — the **signed-in user** is the record whose `principal` field equals the token's `sub` ([glossary](/concepts/glossary/#signed-in-user)). In an arm, `me` is that record, fully typed, no annotation.
- `classes` — the **roles** a token may carry ([glossary](/concepts/glossary/#role)); `P.class` is a claims gate in front of an arm, not an expression.
- The second argument is one block per record type (reads) plus `operations:` (writes). A record type with no `read` is invisible; a registered operation with no arm **denies** everyone but `superuser`.

`Ramose.policy` throws at deploy on an unknown field, class or record type, an empty or duplicate class list, a `principal` outside the schema, a rule the query validator rejects, a rule that never binds its focus as that entity (own field, reverse ref, named rule — not a foreign e-slot), no schema class, or `P.class(superuser)`. `P.class` omits `superuser`; `Ramose.Policy.Class<typeof policy>` is the `classes` union.

Standalone rules annotate `me` once (`(me: Ramose.Policy.Me<typeof User>) => …`). Inline arms write `(me) => …` with `me` typed.

## Reads: per-fact masks

The only per-fact verb is `read`. It is checked on every query, pull and live query — including `asOf` and `history` views. Namespace `read` is the default for every attribute; `P.field` narrows one attribute.

```ts
issue: { read: true, attrs: [P.field(Issue.privateNote, { read: P.class("owner") })] }
```

Each takes one arm or a list (OR). An arm is a fragment, an array of fragments, `true`, or a class gate.

## Writes: per-operation arms

Writes are authorized at the named operation. Body `operations:` keys are registry bindings (typed off `head.operations`) and lower to the wire name. Entity-owned keys also live under the owner (`issue.operations.rename`); trait-owned under `traits.taggable.operations`. An arm matches `read`: `true`, `P.class(...)`, `{ class, rule }`, or an array (OR).

- A **bare** (`self: false` / no-`on`) operation takes a class gate only. A rule fragment is a compile error. A wire arm that still names a rule (or a v1 expression that reads the entity) on a registry-bare op is **denied** at runtime and rejected at deploy — the rule is not ignored.
- An operation with `on:` may name `rule: (me) => fragment`. The rule runs against the **resolved target** before the body executes — one named-rule query with `self` as the focus.
- A registered operation with no arm denies everyone but `superuser`. Reef declares no `superuser`, so an unarmed op there denies everyone; compile-time coverage is what keeps that safe.
- `P.compile(policy, { operations })` and `Ramose.Server({ operations, auth: { policy } })` fail the deploy if an armed name is not in the registry, or if a rule arm is attached to a registry-bare op.

Who-did-this fields (`issue.creator`, `comment.author`) are written from `op.principal` in the operation body. The client does not send them.

```ts title="examples/reef/src/domain/policy.ts#policy-operations"
    operations: {
      provisionWorkspaceOp: P.class("owner"),
      createIssueOp: P.class("owner", "member"),
      seedSampleIssuesOp: P.class("owner", "member"),
      moveIssueOp: { class: ["owner", "member"], rule: ownIssue },
      setStatusOp: { class: ["owner", "member"], rule: ownIssue },
      addCommentOp: P.class("owner", "member"),
      deleteIssueOp: { class: ["owner", "member"], rule: ownIssue },
      setTitleOp: { class: ["owner", "member"], rule: ownIssue },
      setDescriptionOp: { class: ["owner", "member"], rule: ownIssue },
      setPriorityOp: { class: ["owner", "member"], rule: ownIssue },
      setAssigneeOp: { class: ["owner", "member"], rule: ownIssue },
      toggleLabelOp: { class: ["owner", "member"], rule: ownIssue },
      setPrivateNoteOp: P.class("owner"),
      deleteCommentOp: { class: ["owner", "member"], rule: ownComment },
    },
```

## Arms are fragments

| arm | true when |
| --- | --- |
| `true` | always — the empty fragment, public |
| `(me) => Query.is(attr, me)` | the record's `attr` equals the caller; on a many-valued field, contains them |
| `(me) => function* (e) { … }` | the fragment matches with focus `e` and principal `me` |
| `[(me) => a, (me) => b]` | any one fragment matches |
| `P.class("member")` | the caller's role is `member` (must be in `classes`) |
| `{ class: "member", rule: frag }` | the class gate holds **and** the fragment matches |

```ts
// doc → project → org → members contains the caller
const inOrg = (me: Ramose.Policy.Me<typeof User>) =>
  function* (doc) {
    const project = yield* Query.follow(Doc.project)(doc);
    const org = yield* Query.follow(Project.org)(project);
    yield* Query.is(Org.members, me)(org);
  };

const mine = (me: Ramose.Policy.Me<typeof User>) => Query.is(Doc.owner, me);
```

The same `inOrg` value pipes in the app (`pipe(entities(Doc), Query.refine(inOrg(me)))`) and installs as the policy arm — UI filtering and enforcement cannot drift.

Membership, ownership and sharing are facts in the database, not claims in the token. Revoking access is a write; it takes effect on the next version. Relation-based visibility ("issues in a project whose team I belong to") is an ordinary fragment: there is no depth cap and no second language.

`P.class` is a residual JWT claims gate, checked before the rule runs. It composes with fragments (`{ class: "member", rule: ownIssue }`) and never grows expressions. Prefer a role fact when the peer writes one (`Q.fact(me, User.role, "owner")`); keep `P.class` for deployments where the role must stay token-only.

## How rules combine

| situation | verdict |
| --- | --- |
| no `read` for this record type | **invisible** |
| no arm for this registered operation | **denied** (except `superuser`) |
| one allow arm holds | allowed |
| several allow arms, any one holds | allowed |
| a field `read` and its record-type `read` | both must allow — the field rule only narrows |

```ts
// 1. no rule at all for doc → nothing about a document is readable
{}
// 2. one arm: the owner may read their own documents
{ doc: { read: (me) => Query.is(Doc.owner, me) } }
// 3. two arms: the owner *or* anyone in the document's org may read it
{ doc: { read: [mine, inOrg] } }
// 4. narrowed: everything above, except doc.audit, which is owners only
{ doc: { read: [mine, inOrg],
         attrs: [P.field(Doc.audit, { read: P.class("owner") })] } }
```

## Field rules narrow

`P.field(field, rules)` sits under its own record type and can only tighten the record-type rule. A field you add later inherits the record-type rule instead of becoming world-readable.

```ts title="examples/reef/src/domain/policy.ts#policy-private-note"
        P.field(Issue.privateNote, { read: P.class("owner") }),
```

## Standing

| field | meaning |
| --- | --- |
| `superuser` | bypass: unfiltered reads, unchecked writes; `explain`, `/admin/*`. `P.class(superuser)` is unreachable |
| `schemaClasses` | who may grow schema (default `[superuser]`); runs the rules |
| `anonymous` | given to a caller with no token, **only if the policy declares it**; otherwise token-less calls are `Unauthorized` |
| `$token` | the `RAMOSE_TOKEN` holder under a policy; cannot be declared, so no rule admits it |

:::caution
Class `admin` is ordinary unless named `superuser`. `anonymous` is the internet; declare it on purpose.
:::

## Where the checks run

- **Reads are filtered, never rejected.** The server hides the facts you may not read; a list is shorter, a hidden required field makes `pull` return `null` — the same as a missing record. A fragment arm runs as one query-engine query over the *unfiltered* data, always at the *current* version, so reading the past cannot revive a revoked grant. For a named rule the engine first asks for every `e` visible to `me` and the per-fact check is a set lookup; a set that is too large falls back to one query per entity. A rule that blows the query memory budget is a 413 `policy/budget-exceeded`, not an empty result. The live connection follows the same rule: a write you cannot read never appears on it, and a grant or revoke that changes what you can see asks the page to reload its view.
- **Writes are checked at the operation.** `prepareOperation` runs the class gate before touching the db, then the named rule against the resolved `self`, both before the body executes any effect or accumulates any tx. A refusal is the same opaque `Unauthorized` 403 with `code: "policy"` a fact denial is. Raw `/transact` under a configured policy admits schema txs for `schemaClasses` and data txs for `superuser` only — there is no per-fact write vocabulary left to check anyone else against. `writes: "all"` opens raw `/transact` only when no policy is configured. Unknown-op `BadRequest` and input-decode errors fire before the class gate, so a declared-class principal can map registered op names (and `GET /health` lists op ids). That is accepted: no data is exposed.
- **Refusals do not leak values.** An operation denial names neither the target nor a field value.
- **The server fails closed.** A malformed policy, or a policy without a working verifier, denies every `/db/*` request and logs once at start-up. An old-format policy that still carries write arms is malformed in this sense — regenerate `RAMOSE_POLICY` in the same deploy as the engine upgrade, or the data plane stays closed.

## compile and the pulls check

`P.compile(policy, { pulls?, operations? }): string` turns the policy into the JSON `RAMOSE_POLICY` holds. Each fragment arm is promoted to a named query rule (`Query.rule` — return-var-into-head) and written into a `rules` section next to the surviving arms. Rule bodies are validated against the catalog through the query validator (attrs exist, namespaces line up). The wire version is 2; installed policies recompile at deploy.

Pass the shapes your screens read and a masked field pulled as *required* fails the deploy; without `pulls` the check is skipped. `P.checkPulls(policy, pulls)` runs the check alone. Pass the operations registry and an armed name that is not registered, or a rule arm on a registry-bare op, fails the deploy; unarmed registered ops are listed as superuser-only.

```ts title="examples/reef/src/domain/policy.ts#compiled-policy"
export const compiledPolicy = (): string =>
  P.compile(policy, { pulls: allShapes, operations });
```

## The token the server verifies

```json
{
  "iss": "reef-demo-auth",
  "aud": "ramose:reef",
  "sub": "user_01HQ8ZK",
  "iat": 1755499100,
  "exp": 1755500000,
  "ramose": { "db": "coral-team", "class": "member", "attrs": { "org": "org_42" } }
}
```

| claim | rule |
| --- | --- |
| `iss` | in `RAMOSE_JWT_ISS` (comma-separated list) |
| `aud` | equals `RAMOSE_JWT_AUD` |
| `exp` | required; `exp - iat ≤ RAMOSE_JWT_MAX_TTL` (default 900 s) |
| `sub` | non-empty; matched to the `principal` field |
| `ramose.db` | equals the database in the URL — else `Unauthorized` "token is not valid for this database" |
| `ramose.class` | a class the policy declares |
| `ramose.attrs` | optional; your own claims, readable as `P.claim.attrs.<key>` |

Signatures: `RS256`, `ES256` or `EdDSA`, keys from `RAMOSE_JWKS_URL` (or `RAMOSE_JWKS_JSON`). Sent as `Authorization: Bearer …`, or `?token=` on the WebSocket upgrade. Ramose verifies tokens; it never issues them — see [Sign in and roles](/guides/sign-in/#what-the-token-carries) for minting with `Ramose.claims` and `ramose/better-auth`.

```ts
Ramose.claims(auth, { sub, db, class, attrs? }, policy?)  // policy value narrows `class`; compiled JSON still accepted
```

## Server env keys

Set `auth: { policy, jwt, jwksUrl, … }` and `token` on `Ramose.Server`. That is the source of truth; Server writes these keys onto the Worker. Do not also hand-copy `RAMOSE_*` onto a Worker env.

```ts title="examples/reef/src/infra/resources.ts"
export const Server = Ramose.Server("Ramose", {
  env: { AUTH: Api },
  auth: {
    policy: compiledPolicy(),
    jwt: REEF_AUTH,
    jwksService: "AUTH",
    jwksUrl: /* Output over the auth Worker */,
    allowedOrigins: /* Output over the SPA origin */,
  },
});
```

| key | env var | meaning |
| --- | --- | --- |
| `token` (Server prop) | `RAMOSE_TOKEN` | shared bearer; owned form binds it |
| `policy` | `RAMOSE_POLICY` | the compiled JSON; setting it arms enforcement |
| `jwksUrl` | `RAMOSE_JWKS_URL` | where the sign-in provider publishes its public keys |
| `jwksService` | `RAMOSE_JWKS_SERVICE` | service binding to fetch `jwksUrl` through; needed when the provider is a Worker on your account ([Server](/reference/server/)) |
| `issuers` | `RAMOSE_JWT_ISS` | accepted `iss` values |
| `aud` | `RAMOSE_JWT_AUD` | the required `aud` |
| `maxTtl` | `RAMOSE_JWT_MAX_TTL` | cap on token lifetime, seconds (default 900) |
| `allowedOrigins` | `RAMOSE_ALLOWED_ORIGINS` | CORS list; honoured only once a policy is set |
| `internalSecret` | `RAMOSE_INTERNAL_SECRET` | Worker-to-writer gate; minted for you when unset and a policy is set. **Strongly recommended in production** — the gate is only armed when the secret is set |
| `writes` (Server prop) | `RAMOSE_WRITES` | `"operations"` (default) closes raw `/transact` for app-class tokens; `"all"` is the opt-out. See [The server](/reference/server/) |

`jwt: { issuer, audience, ttl }` fills `issuers`, `aud` and `maxTtl` from one value. Which mode a server runs in — open, shared token, or policy — is decided by `RAMOSE_POLICY` and `RAMOSE_TOKEN`: see [The three server modes](/guides/permissions/#the-three-server-modes).

## Testing without a login provider

`RAMOSE_JWKS_JSON` takes a literal key set instead of a URL, so a local server can verify tokens you sign yourself.

<details>
<summary>Sign your own tokens with jose</summary>

```ts title="scripts/local-jwt.ts"
import { SignJWT, exportJWK, generateKeyPair } from "jose";

const { privateKey, publicKey } = await generateKeyPair("ES256", { extractable: true });

// 1. the server's verifier — set this as RAMOSE_JWKS_JSON
console.log(JSON.stringify({
  keys: [{ ...(await exportJWK(publicKey)), alg: "ES256", kid: "local" }],
}));

// 2. a token for one user of one database
console.log(
  await new SignJWT({ ramose: { db: "todos", class: "member" } })
    .setProtectedHeader({ alg: "ES256", kid: "local" })
    .setIssuer("https://local.test")
    .setAudience("ramose:local")
    .setSubject("user_ada")
    .setIssuedAt()
    .setExpirationTime("5m")
    .sign(privateKey),
);
```

Then on the owned Server: `auth: { policy, issuers: "https://local.test", aud: "ramose:local" }` plus `env: { RAMOSE_JWKS_JSON: process.env.RAMOSE_JWKS_JSON }`. Run `bun alchemy dev` with `RAMOSE_JWKS_JSON` set to line 1 of the script's output, and hand line 2 to the client as `Ramose.token.static(token)`. Generate both once — every run mints a fresh key pair. Reef does not need this: its Better Auth Worker signs tokens locally.

</details>

## Limits

- One policy per deployed server, over one schema; no per-database variants.
- No cross-database rules.
- 413 bodies (`clause`, `cells`, `limit`, `spentBy`) and the `x-ramose-*` timing headers are not policy-filtered. `spentBy` is `policy` when a conjoined visibility rule spent the budget, `caller` otherwise.
- Reads conjoin each namespace rule into the query before planning (a two-view join: the rule reads the unfiltered db, the caller's clauses the filtered view). `FilteredDb` remains the backstop for pull, history, raw fact access, and attribute-level narrowing.
