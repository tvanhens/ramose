Ramose policy has two public decisions: what facts a principal may read, and which exact operations the principal may invoke. Both compile against the catalog and run server-side.

*New here? Start with [Permissions](/guides/permissions/).*

## Read policy

```ts
const readPolicy = Ramose.Policy.compileReadAuthorization({
  catalog: ProjectCatalog,
  principal: Account.sub,
  rules: {
    task: Ramose.Policy.read.when(isProjectMember),
    privateNote: Ramose.Policy.read.when(isOwner),
  },
})
```

Read authorization produces an immutable filtered database capability. All queries, relationship traversal, rule evaluation, counts, graph lookup, and target resolution run against it. The runtime does not query everything and filter the final rows.

Entity-level rules govern facts for a type. Field rules may narrow especially sensitive attributes. A field rule cannot widen an entity rule.

## Invoke policy

```ts
const invokePolicy = Ramose.Policy.compileInvocations({
  catalog: ProjectCatalog,
  grants: [
    Ramose.Policy.invoke(Task.setDone).when(isProjectMember),
    Ramose.Policy.invoke(Task.delete).when(isOwner),
    Ramose.Policy.invoke(createTask).when(isProjectMember),
  ],
})
```

Grants name operation definition values, not unchecked strings. A targeted call also requires a visible target compatible with the owner. A targetless call requires the exact grant only.

## Principal

The principal is derived from a verified token and matched through the configured catalog field. Token claims may supply stable identity and trusted coarse attributes; mutable membership and ownership normally belong in graph data so policy changes synchronize like other facts.

## Graph context

Policy is evaluated for one authorized graph. Traversing a child graph first resolves and authorizes every parent binding. The child then applies its own catalog and policy to reads and operations.

## Composition

Build small named rule fragments for roles, membership, ownership, relationships, and classes. Compose them with policy `and`, `or`, and `not` rather than duplicating logic across entities and operations.

Recursive rules must be bounded and compile without access to fields the rule itself masks. Catalog compilation rejects unknown definitions, incompatible targets, and invalid dependency cycles before deployment.

## Failure behavior

Policy configuration fails closed. A missing or invalid policy does not fall back to public access. Hidden, missing, wrong-type, and unauthorized targets collapse to public `inaccessible` or operation rejection behavior where a distinction would disclose facts.

Client-side role checks are presentation hints only. They may hide unavailable controls but never replace server enforcement.
